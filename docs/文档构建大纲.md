# 文档构建大纲

> 版本：v2.2  
> 用途：指导七份目标文档的拆分、编写顺序与边界。本文是文档规划框架，不替代比赛要求或 PRD，也不预写目标文档的业务、接口、数据结构和测试细节。

## 一、依据与使用原则

### 1.1 上游依据

- 《比赛作品要求.md》：比赛目标、硬性技术要求和作品交付要求。
- 《AI_Banking_Agent_需求规格说明书.md》（PRD-ABA-001 v2.0）：产品范围、P0/P1/P2、安全不变量、六场景需求与验收基线。
- 原大纲提及的“本复审统一基线”未随本次材料提供，状态为**待补充**；在补充前不得把它作为设计或验收依据。

发生冲突时，按比赛要求、PRD 不可妥协基线、PRD 其他 P0、PRD P1/P2 的顺序处理。本大纲不得扩大或削弱上游范围。

### 1.2 编写原则

1. 本大纲只规定每份文档的目的、边界、主题、依赖和完成条件；具体规则、字段、流程、方案和测试步骤由对应目标文档编写。
2. 七份文档共同覆盖比赛要求及 PRD 全部 P0。需求 ID 应在目标文档及其追踪表中映射，本大纲不重复抄录需求正文。
3. 比赛硬指标、PRD P0 和项目为安全/可验收性增加的 P0 应在目标文档中区分来源；项目扩展项不得标成比赛逐字要求，也不得因此降级。
4. PRD 中的 P1/P2 不能成为 P0 的隐含前置条件。未定义的金融写能力不得自行加入。
5. 密码/PIN 修改及其可执行工具不属于本项目范围；不得因比赛示例而实现。
6. 未由上游确定的技术选型和运行参数由后续文档说明决策依据；不得在本大纲中臆定。

## 二、七份目标文档及边界

### 1. 项目开发总架构文档（DOC-ARCH-001）

**目的**：建立全项目的技术与安全架构基线，明确系统组成、职责边界和开发约束。

**内容框架**：总体架构与模块关系；技术和运行环境决策；分层与代码组织原则；安全、权限、风险、审计、隐私及沙箱的架构承接；开发协作、版本和变更规则；比赛技术资料的架构内容来源。

**边界**：定义跨模块原则，不重复接口契约、数据库设计、场景流程或测试用例。

### 2. 统一数据与接口契约文档（DOC-CONTRACT-001）

**目的**：为前后端、服务、Agent、工具、数据库之间建立一致的交互和数据约定。

**内容框架**：契约表达方式与版本策略；公共对象和业务对象分类；接口、事件、工具的契约范围；状态与错误表达原则；安全上下文、数据可见性和脱敏约定；契约变更及兼容管理。

**边界**：提供跨模块一致性定义，不替代业务规则、架构决策或数据库物理实现。

### 3. 前期项目基座构建文档（DOC-FOUND-001）

**目的**：指导从空仓库构建可启动、可开发、可演示的项目基础设施。

**内容框架**：仓库与目录初始化；本地运行和服务编排；前后端基础骨架；认证、租户和资源隔离基础；数据迁移与演示数据；沙箱、模型网关、工具治理和安全服务的基础接入；健康检查、重置、README 与启动验证。

**边界**：交付可运行基座，不提前宣称六场景业务完成；场景功能由进阶前后端文档承接。

### 4. 进阶前后端开发文档（DOC-APP-001）

**目的**：指导用户交互与服务端业务能力的完整实现。

**内容框架**：交互信息架构与任务状态呈现；前后端职责和接口使用；统一对话流程；六场景的功能拆分与页面/API/服务映射；确认、风险、人工处理、异常恢复和结果反馈；权限可见性与运营视图。

**边界**：按 PRD 的 FR 组织业务实现，不重新定义契约、数据库规范或 Agent 内部编排机制。

### 	5. 进阶数据库文档（DOC-DB-001）

**目的**：指导业务数据、状态、权限隔离、审计和可核对事实的持久化设计。

**内容框架**：数据域与实体关系；表结构设计方法；数据类型、完整性、索引和版本管理原则；租户/资源隔离、敏感数据保护、审计保留、幂等和异步事件的持久化承接；迁移、种子和重置策略。

**边界**：由契约和 PRD 派生数据库实现，不改变业务状态含义或另行增加需求。

### 6. Agent 系统设计文档（DOC-AGENT-001）

**目的**：指导 LangGraph 任务编排、领域能力协作和安全执行路径设计。

**内容框架**：Agent/图的职责边界；状态与计划的组织原则；路由、澄清、计划、执行、恢复和人工介入的编排；工具接入与安全控制；模型输入输出治理；中断、恢复、重规划和可追踪性。

**边界**：说明 Agent 如何调用契约定义的能力，不重复业务接口和数据库定义；不得让模型或子 Agent 绕过公共安全控制。

### 7. 测试文档（DOC-TEST-001）

**目的**：建立需求验收、风险验证、发布阻断和比赛交付的测试框架。

**内容框架**：测试策略、层级、环境和数据原则；需求追踪方法；功能、安全、异常恢复和稳定性测试范围；验收证据管理；发布阻断和缺陷闭环；比赛交付物核对。

**边界**：测试对象来自比赛要求和 PRD，不在测试文档中新增产品需求；具体用例、数据和执行步骤在该文档内编写。

## 三、横向协作与文档依赖

### 3.1 编写顺序

1. 先编写 DOC-ARCH-001，确定总体边界与共同原则。
2. 再编写 DOC-CONTRACT-001，固化跨模块接口与数据约定。
3. 基于架构和契约编写 DOC-FOUND-001，搭建可运行基座。
4. DOC-APP-001、DOC-DB-001 与 DOC-AGENT-001 在架构和契约约束下分别展开，可并行编写，但须共同评审接口、状态和职责边界。
5. DOC-TEST-001 随需求和设计同步建立追踪，并在各文档定稿后完成验收用例和发布门禁。

### 3.2 共同约束

七份文档都必须遵守上游范围、安全和验收基线，至少保持以下主题口径一致：

- 需求来源及比赛硬指标、PRD P0、项目扩展 P0 的来源区分；
- 六场景及统一交互、安全权限、确认与人工处理；
- 沙箱事实边界、模型/工具职责、安全失败处理；
- 状态、数据、审计、幂等、隔离、脱敏及演示环境；
- 需求追踪、变更影响、验收和发布阻断。

各主题的具体规则由职责最匹配的文档定义；其他文档引用其定义，不再复制一套独立版本。DOC-CONTRACT-001 负责承载跨模块字段、状态、事件及错误表达的一致定义；其内容变化时，相关文档同步评估。

## 四、每份目标文档的最低完成条件

每份目标文档定稿前均须满足：

1. 说明目的、适用范围、非范围、上游来源和依赖文档；
2. 说明其承接的比赛要求、PRD 章节/FR ID，未承接部分有明确理由；
3. 有足以指导该文档负责工作的章节结构，细节放在目标文档正文，而不是本大纲；
4. 与其他目标文档不存在未处理的术语、职责或约定冲突；
5. 给出本文件自身可审查的 DoD、验收方式和应归档的证据类型；
6. 对待确认事项和变更影响作出记录，不以未提供的资料补造结论。

DOC-TEST-001 负责汇总需求到设计、测试和演示/交付证据的追踪关系。所有 PRD P0 均需有对应验收路径；比赛交付项均需有负责文档和完成证据。具体矩阵由 DOC-TEST-001 编制。

## 五、范围与交付约束

- 目标文档总数固定为七份；不通过本大纲新增第八份目标文档。
- 比赛要求的架构图、核心算法说明、安全设计和安全自评，应映射到上述文档及比赛提交材料中；作品简介、答辩和视频按比赛要求准备，不把这些内容扩展成新的产品功能。
- 首版基线保留 CNY、Asia/Shanghai、合成数据、银行/礼品沙箱、金额精确表达、幂等、审计、确认、模拟 MFA、人工复核和 fail-closed。其具体设计分别进入架构、契约、数据库、Agent、前后端及测试文档。
- 禁止真实资金、真实客户数据、真实第三方下单及 PRD 明确排除的真实金融能力；P1/P2 只按上游界定，不得隐性并入 P0。
- 需求范围、权限、安全条件或验收口径变化时，先按上游变更流程评估，再同步受影响的七份文档和追踪记录。

## 六、配套实现说明文档
