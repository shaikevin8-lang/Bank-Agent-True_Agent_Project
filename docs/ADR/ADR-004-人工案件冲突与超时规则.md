## 1. 背景

P0 要求「最小人工复核」，而「最小」在这里是**能力边界**，不是**实现省略**：单案件、单审核员、通过/拒绝/补件、理由、审计（需求 `:240`）。只要系统允许两个操作员同时点「批准」，或允许一个案件无限期挂着，最小闭环就会立刻退化成两类事故：

- **双花**：两个操作员同时批准同一笔高风险转账，重放两次；或者一次批准一次拒绝，账务与审计自相矛盾。
- **悬案**：案件永远停在 `open`，用户侧一直显示「等待人工处理」，系统既不执行也不释放；未知结果积压而无人察觉（架构 `:179` 要求人工案件必须告警）。

第二条约束来自角色表：需求 `:73`/`:74` 明确要求**职责分离**——审核员只能处理分配给自己的案件且不能代替用户确认，运营能重置数据但**不能审批**。因此「谁能改案件」不是流程纪律，必须是服务端强制。

超时也必须明确定义，而且默认方向只有一个：**fail-closed**。需求 `:108` 要求审批不可用时写操作不得自动执行，`:220` 要求红色动作「不得自动放行」。所以「超时自动批准」没有技术讨论空间——但为了把理由固化下来，仍列在 §4。

## 2. 决策

### D1 单案单认领独占

- 一个案件同一时刻最多一个 `assignee`；`assignee IS NULL` 表示无人认领。
- 认领（`POST /api/hitl/cases/{case_no}/claim`）只允许从 `open`/`info_required` 迁移到 `claimed`，写入 `assignee`、`claimed_at`、`claim_expires_at`（= 认领时**业务时间** + 认领 TTL）。
- 决策（`approve`/`reject`/`request_info`）**必须由当前 `assignee` 本人发起**；非认领人决策返回 `409 case_not_claimable`。「单审核员」不是靠流程纪律，而是靠状态机 + 条件更新。
- 身份取两个请求头：`X-Role: user|risk_reviewer|ops_admin`（缺省 `user`）+ `X-Operator: <名字>`。`claim`/`decision` 仅 `risk_reviewer` 可调用；`ops_admin` 越权 → `403 role_not_allowed`（需求 `:74`「不能审批或代替用户执行金融写入」），`user` 亦同（需求 `:73`「不能代替用户确认」，也不能自己批自己的案件）。

### D2 `version` 乐观锁

- `app.hitl_case.version` 从 1 起，每次成功迁移 +1。
- 所有状态迁移用条件更新，语义等价于：

```sql
UPDATE app.hitl_case
   SET status = :to, version = version + 1, ...
 WHERE id = :id AND version = :expected AND status = :from;
```

`rowcount = 0` → 说明有人抢先改了 → 返回 `409 case_version_conflict`，并在 `data.case` 里返回**最新**案件快照，前端据此刷新而不用猜。

- 客户端可传 `expected_version`；不传时服务端用「本次请求读到的版本」，仍然受条件更新保护。

### D3 认领 TTL 到期可被他人回收（惰性判定，不靠定时器）

- 认领 TTL 默认 **300 秒**，可通过 `BANK_AGENT_HITL_CLAIM_TTL_SECONDS` 调整（需新增配置项）。
- 回收是**惰性**的：`claim`/`decide`/`GET` 路径发现 `status='claimed' AND claim_expires_at <= business_now` 时先回收：

```sql
UPDATE app.hitl_case
   SET status = 'open', assignee = NULL, claimed_at = NULL, claim_expires_at = NULL, version = version + 1
 WHERE id = :id AND status = 'claimed' AND claim_expires_at <= :business_now;
```

并写一条 `hitl_case_event(action='claim')` 之外的补偿事件——回收在事件流里以 `action='claim'` 的兄弟记录表达会导致语义混淆，因此**回收复用 `claim` 事件并强制 `note` 前缀「认领超时自动回收」**（不新增事件枚举，保持实施计划 §2.3 的事件枚举封闭）。回收后他人可正常认领。

- **明确不做**：后台常驻定时器扫描认领过期（非目标，见设计说明 §2）。演示环境下多一个后台线程只是多一个不可审计的并发源；惰性判定 + 条件更新语义等价且天然幂等。

### D4 三种决策，其中 `request_info`（补件）回流

决策只有三种（需求 `:144`「只提供最小闭环：单案件、通过/拒绝/补件、理由和审计」）：

| 决策 | 迁移 | 副作用 | `note` |
| --- | --- | --- | --- |
| `approve` | `claimed → approved` | 恢复执行（重走安全门 + 幂等键） | 建议填写 |
| `reject` | `claimed → rejected` | 不执行，生成面向用户的拒绝说明 | **必填** |
| `request_info` | `claimed → info_required` | 不执行，通知用户补充资料，**SLA 重算**（`expires_at = business_now + sla_seconds`），释放认领 | **必填** |

- `info_required` 是「补件后的等待态」：`assignee=NULL`，可被任何 `risk_reviewer` 重新认领（`info_required → claimed`），SLA 从补件时刻重新起算。它与 `open` 的区别是**来源**（`open` = 新案件，`info_required` = 补件后重开），处理能力完全相同。
- 实施计划 §1.2 把它描述为「案件回到 `open`」，而 §2.3 的状态枚举含 `info_required`；本 ADR 取「落在 `info_required`、语义等价于回到未认领等待态」，避免同一案件在同一事件里做两次迁移。措辞差异已列入设计说明「对实施计划的偏差建议」。
- 补件不能变成「无限续命」：`info_required` 同样受 `expires_at` 约束，且每个案件的重开次数在 `hitl_case_event` 里可数。

### D5 重复决策幂等：返回首次结果

- 决策成功后 `status ∈ {approved, rejected, info_required}`，`decision` JSONB 固化决定内容（`decision`、`operator`、`note`、`business_at`、`resumed` 摘要），并另存 `decision_note`（拒绝/补件理由）与 `info_request_note`（补件说明）。
- 对已决策案件再次提交决策：
  - 与已存 `decision` **一致**（同 `decision` 值、同 `operator`、`note` 相同或省略）→ **200 + 首次结果**，`data.replay=true`，不产生新副作用、不新增 `audit.event`（幂等重放不是一次新决定）。
  - **不一致**（先 reject 后 approve、换操作员、理由不同）→ `409 case_already_decided`，绝不覆盖首次结果。
- 批准后执行写操作本身还有一层幂等键：复用 `Struct_of_Agent/db/idempotency.py` 的 `begin_operation(...)`/`complete_operation(...)`，`operation_type` = 工具名，`key_value` = `proposal.idempotency_key`。即使 API 层幂等被绕过（进程重启后重放），也不会产生第二次扣款。

### D6 SLA 默认 15 分钟，全程用业务时钟

- `sla_seconds` 默认 **900**（15 分钟），可由 `BANK_AGENT_HITL_SLA_SECONDS` 调整（需新增配置项），创建案件时固化到行里（改配置不影响在途案件）。
- `expires_at = business_at + sla_seconds`，`business_at` = 创建案件时的业务时间（`Clock.now()`）。
- 倒计时、过期判定、`claim_expires_at` 全部以**业务时间**为基准。演示时钟推进时 SLA 跟着跳，冻结时 SLA 停止推进——这正是演示需要的可控性（冻结时钟讲解时案件不会莫名过期）。前端倒计时仅用于渲染，**判定权在服务端**。

### D7 超时 → `expired`，fail-closed，不执行任何副作用

- 过期扫描由 `POST /api/hitl/sweep`（可带 `now`，缺省取业务时间）驱动，覆盖 `open`/`claimed`/`info_required` 三态：

```sql
UPDATE app.hitl_case
   SET status = 'expired', version = version + 1, updated_at = now()
 WHERE status IN ('open', 'claimed', 'info_required') AND expires_at <= :business_now;
```

每个命中案件写 `hitl_case_event(action='expire')` + `audit.event`，响应 `data.expired=[case_no]`。

- 过期案件**不执行**原提案：不调用工具、不产生任何账务或外部副作用，`proposal` 只作为证据留在行里。
- 用户侧必须收到明确说明：「本次请求已超过人工复核时限，未执行任何操作，可重新发起」。重新发起创建**新案件**（新 `case_no`、新 `sla_seconds`、新业务时间），不复用旧案、不允许「延长旧案」，以免出现「同一案件两次不同的批准时间」这种无法审计的状态。
- 与审计/风控不可用叠加：任一时点写审计失败 → 整个事务回滚，写操作与状态变更都不生效（架构 `:199`）。

### D8 合法迁移矩阵（唯一真相，服务层强校验）

| # | from | to | 触发动作 | 允许角色 | 事件 `action` |
| --- | --- | --- | --- | --- | --- |
| 1 | `open` | `claimed` | `claim` | `risk_reviewer` | `claim` |
| 2 | `info_required` | `claimed` | `claim`（重新认领） | `risk_reviewer` | `claim` |
| 3 | `claimed` | `open` | 认领 TTL 到期回收（系统） | 系统 | `claim`（note 前缀「认领超时自动回收」） |
| 4 | `claimed` | `approved` | `decision: approve` | 认领人 | `approve` + `resume` |
| 5 | `claimed` | `rejected` | `decision: reject` | 认领人 | `reject` |
| 6 | `claimed` | `info_required` | `decision: request_info` | 认领人 | `request_info` |
| 7 | `open` | `cancelled` | `cancel` | `risk_reviewer` / 系统（策略停机） | `cancel` |
| 8 | `claimed` | `cancelled` | `cancel` | `risk_reviewer` / 系统 | `cancel` |
| 9 | `info_required` | `cancelled` | `cancel` | `risk_reviewer` / 系统 | `cancel` |
| 10 | `open` | `expired` | `sweep` | 系统（业务时间） | `expire` |
| 11 | `claimed` | `expired` | `sweep` | 系统 | `expire` |
| 12 | `info_required` | `expired` | `sweep` | 系统 | `expire` |

终态：`approved` / `rejected` / `expired` / `cancelled` —— 任何从终态出发的迁移均为非法（`409 invalid_transition`）。其余组合（如 `open → approved`、`claimed → claimed`）同样非法。

## 3. 结果与后果

### 3.1 正面

| 收益 | 说明 |
| --- | --- |
| 双花在协议层不可能 | 单认领 + 条件更新 + `version` 三重约束，同一案件最多一个请求能改动 |
| 无副作用超时可证明 | `expired` 案件的 `hitl_case_event` 里没有 `approve`、也没有工具执行审计，审计可回放证明「什么都没做」 |
| 补件有明确出口 | `request_info` 不再被塞进 `reject`，用户侧看到的是「请补充资料」而不是「已拒绝」 |
| 职责分离可测 | `403 role_not_allowed` 是一条可断言的边界，而不是注释里的君子协定 |
| 演示确定性 | SLA 与认领 TTL 都按业务时钟计算，推进/冻结可复现 |

### 3.2 负面与代价

| 代价 | 缓解 |
| --- | --- |
| 认领人掉线会把案件挂到 TTL 结束 | TTL 默认 300 秒且有倒计时；到期后他人可立刻接手 |
| 惰性回收意味着「过期」在有人访问时才落地 | 前端队列抽屉定期调用 `POST /api/hitl/sweep`；`GET /api/hitl/cases` 也会触发判定 |
| 同操作员两个标签页操作同一案件 | `version` 条件更新让后到者得到 `409 case_version_conflict`，前端刷新即可 |
| 补件会拉长案件寿命 | `info_required` 同样受 `expires_at` 约束；重开次数可从事件流统计 |
| 「不一致重复决策」只能报错 | 这是特性：一旦决定不可撤回；要改只能走新的业务请求 |

## 4. 被否决的备选方案

### 4.1 备选 A：超时自动批准

否决理由：

1. **直接违反需求**：需求 `:220` 规定红色动作「命中策略时人工复核；不得自动放行」；`:108` 规定审批不可用时写操作不得自动执行。自动批准等于把「无人处理」解释成「同意」，与 fail-closed 相反。
2. **审计无法解释**：`decided_by` 没有真人、`decision_note` 为空，`audit.event` 里出现一条「系统批准了一笔 1000 元以上转账」，事后无法回答「谁批准的」。
3. **与确认分离原则冲突**：需求 `:142` 要求人工通过不能代替用户确认；自动批准在一次无人响应的链路上同时完成两件事。
4. **激励错误**：拖着不处理就能让高风险动作通过，等于把「不作为」变成可利用的批准通道。

### 4.2 备选 B：多操作员并发批准（先到先决、后到覆盖；或双方都执行）

否决理由：

1. **违反「单案件、单审核员」**：需求 `:142` 明确单案件单审核员；`:73` 规定审核员处理「分配给自己的」案件。
2. **双花与矛盾结果**：两人同时批准 → 若都执行就是两次副作用；若一个批准一个拒绝，最终状态取决于写库顺序，`decision` 与 `resumed` 会对不上。
3. **审计归属不明**：`decided_by` 只能记一个名字，另一个人的操作要么丢失要么伪造。
4. **幂等键救不了**：幂等键只保证「同一决定不重复」，无法仲裁「批准 vs 拒绝」的冲突。
5. **可观测性坍缩**：`version` 之争会变成频繁 409/500，运营看到的是「系统坏了」而不是「有人抢单」。

### 4.3 备选 C：不引入 `version`，用 `SELECT ... FOR UPDATE` 长事务覆盖认领到决策全过程

否决理由：

1. 认领与决策是两次独立 HTTP 请求，中间可能隔几分钟；跨请求长事务长时间占用连接与行锁，浏览器一关就留下未释放锁。
2. 与「写审计同事务」叠加后，审计写入被拖到分钟级，回滚代价巨大。
3. `version` 乐观锁是短事务 + 条件更新，冲突代价只是一次 409 重试。

### 4.4 备选 D：允许「延长旧案件 SLA」代替「重新发起新案件」

否决理由：延长会改写 `expires_at` 语义（同一行先后出现两个 SLA 期限），而 `hitl_case_event` 只能记录动作、无法洗清「被宽限过几次」；重新发起新案件天然保留两次请求的完整证据链，代价只是多一行。

### 4.5 备选 E：允许 `ops_admin` 代办审批（「运营在场就顺手点了」）

否决理由：需求 `:74` 明文「不能审批或代替用户执行金融写入」「不能代替用户确认」（`:73` 同理）。职责分离在演示系统里最容易被临时便利性破坏，而它恰好是验收里「人工复核与用户确认分离、不能被 Agent/UI/配置绕过」这一条（架构 `:195`）的直接对象。
