## 1. 背景

演示时钟存在的理由很具体：R1 的定时转账、R5 的周期扣费提醒、R6 的生日工作流都以「到点」为触发条件，而比赛现场没有人愿意等一天。因此系统需要一个**可被操作员显式推进、可冻结、可回退到真实时间**的业务时钟，让「到期」在几秒内发生。

一旦接受「时钟是可以被推进的」，就必须回答一个绕不开的问题：**进程重启之后，时钟停在哪里？**

这个问题有三个候选答案，代价差别极大：

1. 重启后回到真实时间（时钟状态只活在内存里）；
2. 重启后停在重启前的演示位置（时钟状态持久化）；
3. 不提供演示时钟，所有定时能力靠改数据实现。

本仓库当前的定时能力与演示脚本已经要求「推进到明天，看生日蛋糕礼盒下单」这类跨日演示，而一次演示中间很可能发生 uvicorn 重载、`.env` 修改、SQLite→PostgreSQL 切换、甚至评委要求「重启一下再讲一遍」。因此重启语义不是实现细节，而是演示可行性的组成部分。

架构文档 `:119` 已经把结论的一半写死了：**演示时钟只影响业务触发判断**。也就是说时钟位置是「业务判断的输入」，而不是「一次请求的临时参数」——凡是被业务判断长期依赖的输入，都必须与业务数据同生命周期。

## 2. 决策

### D1 时钟状态持久化在 `app.sim_clock` 单行

- 表 `app.sim_clock`，主键 `id`，**恒为 1**（`CHECK (id = 1)`，约束名 `ck_sim_clock_single_row`）。单行表是「全局唯一业务时钟」这一需求的物理表达：不存在「这个请求用北京时间、那个请求用偏移 +2h」的分叉可能。
- 状态四元组：`enabled`（是否启用演示时钟）、`offset_seconds`（相对真实时间的偏移秒数）、`frozen_at_business`（冻结时的业务时刻）、`version`（乐观锁版本号）。
- 进程内 `SimClock`（需新增，`common/clock.py`）只是这行的**读缓存 + 计算公式**，不是真源；写入一律先落库、同事务写审计，再更新缓存。

### D2 重启后**保持**演示位置

重启（含进程崩溃、`uvicorn --reload`、服务重部署）后，`SimClock` 从 `app.sim_clock` 重新装载，业务时间继续停在重启前的位置（或继续按原偏移滑动，见 D4）。**不回到真实时间**。

装载发生在 `common/clock_store.py`（需新增）的惰性初始化路径：首次调用 `get_clock()` 时在一个 `session_scope` 里读取该行；行不存在则插入默认行（`enabled=false, offset_seconds=0, frozen_at_business=NULL, version=1`）。表结构由迁移保证（`Struct_of_Agent/db/session.py:assert_schema_current` 只校验版本、不建表），因此「行不存在」只会出现在「迁移已执行但从未启用演示时钟」的正常情形。

### D3 业务时间 = 真实时间 + 偏移；时区固定 Asia/Shanghai

```
enabled = false                        -> now() == real_now()
enabled = true  and frozen_at_business is NULL  -> now() = real_now() + offset_seconds
enabled = true  and frozen_at_business is not NULL -> now() = frozen_at_business
```

- `Clock.now()` 返回**业务时间**，`Clock.real_now()` 返回**真实时间**，两者都是 tz-aware，时区固定 `Asia/Shanghai`（架构文档与数据库设计文档均以 CNY + Asia/Shanghai 为首版基线）。
- 存储层一律 `timestamptz`（UTC 语义），只在边界（API 响应、前端渲染、审计展示）转 `Asia/Shanghai`。偏移量以**秒**为单位存取，避免「+1 个月」这类不一致的日历运算。
- 禁止其它模块直接用 `datetime.now()` / `datetime.utcnow()` 取业务时间：业务时间只有一个入口。

### D4 「真实时间仍在走」——偏移滑动与冻结的区别

这是本 ADR 最容易被误解的一条，单独写清：

| 状态 | 业务时间 | 真实时间 | 含义 |
| --- | --- | --- | --- |
| `enabled=false` | 跟随真实时间 | 走 | 正常演示，界面显示「真实时间」 |
| `enabled=true`、未冻结 | `real_now() + offset` | 走 | 演示世界整体平移了 +2h，之后两边**同速前进**；过了 5 分钟真实时间，演示世界也过了 5 分钟 |
| `enabled=true`、已冻结 | 常量 `frozen_at_business` | 走 | 演示世界停表，真实世界继续；SLA 倒计时、到期判断全部停止推进 |

因此在**任何**状态下，`audit` 与领域事件表的 `real_at` 都持续前进；只有 `business_at` 可能停住。复位（`POST /api/clock/reset`）把状态退回第一行。

### D5 一键重置：`POST /api/clock/reset`

- 语义：`enabled=false, offset_seconds=0, frozen_at_business=NULL, version=version+1`，`updated_by=operator`，`updated_at/real_at=now()`。重置后业务时间立即等于真实时间。
- 重置**只影响时钟**，不删除任何业务数据，也不删除任何审计行（架构 `:126`：重置业务数据不得静默删除审计）。业务数据的重置是另一条独立链路：`Struct_of_Agent/db/reset.py` 的 `reset_demo_data(...)`（确认短语常量 `RESET_CONFIRMATION="RESET-DEMO-DATA"`）。两者互不调用，避免「重置时钟就清库」这种不可解释的耦合。
- 重置必须二次确认（请求体 `ack=true`）并写审计：`audit.clock_event`（`action='reset'`，`before`/`after` 全量快照）+ `audit.event`（`append_event`）。历史 `clock_event` 行只追加、不更新、不删除，因此「这次演示推进过几次、谁推的」始终可回放。

### D6 数据库不可读时 fail-closed，不静默退回真实时间

`app.sim_clock` 读取失败（连接中断、迁移未执行）时，`get_clock()` 抛出 `ClockStoreUnavailable`（需新增），API 返回 `503` + `error_code="clock_store_unavailable"`；此时**受时钟影响写操作一律拒绝**（架构 `:199` fail-closed）。

明确否决「读不到就当真实时间」这种降级：那会让一次数据库抖动变成「演示世界瞬移到真实时间、所有定时任务一起到期」，比直接报错危险得多。

### D7 多进程/多实例：以数据库行为唯一真源

演示环境通常是单 uvicorn 进程，但 `--reload`、`live_server` 测试夹具、并发请求都可能同时存在多个读取者。因此：

- 进程内缓存必须有失效边界（读请求直接查库；或缓存 TTL ≤ 1 秒，并在每次 `advance/freeze/resume/reset` 后主动失效）。
- **非目标**：不做集群级时钟同步、不做分布式定时器、不做跨实例调度选举。多实例只是「都读同一行」，语义仍然是单一全局时钟。

### D8 时钟操作受职责分离约束：只有 `ops_admin` 能改

- `/api/clock/*` 的**写操作**（`advance`/`freeze`/`resume`/`reset`）仅允许 `X-Role: ops_admin`；`user`、`risk_reviewer` 越权 → `403 role_not_allowed`，并且**这次越权本身要写一条 `audit.event`**（`action` 见设计说明 §7.1）。
- `GET /api/clock` 允许任何角色读取（前端徽标需要），但只返回状态，不构成权限提升。
- 依据：PRD `:74`「管理员/运营演示角色：管理演示配置、重置数据…不能审批或代替用户执行金融写入」——反向约束同样成立：`risk_reviewer` 不得推进时钟，否则「审核员推进时间让自己的案件过期/提前到期」会变成一条自证清白的后门。
- `operator`（`X-Operator`）只用于**归属与追溯**，不用于鉴权；鉴权只看 `X-Role`。

### D9 明确不是本 ADR 的范围

- **数据重置**（`db/reset.py` 的 `reset_demo_data`）是另一个 P0 能力，不在本次交付范围；本文只在 D5 说明「时钟重置不复用数据重置」，避免两者语义混淆。
- 业务时区可切换、按会话独立时钟、按场景独立偏移，均为非目标。
- `app.sim_clock` 单行表不做软删除、不做历史版本表（历史由 `audit.clock_event` 承载）。

## 3. 结果与后果


### 3.1 正面

| 收益 | 说明 |
| --- | --- |
| 演示可中断可续讲 | 重启后接着讲，不需要重新推进两个小时 |
| 审计可回放 | 每次时钟变更都有 `before`/`after` 与 `real_at`/`business_at`，能证明「这个订单是在演示时间 10:00 触发的」 |
| 验收可直接对应 | 实施计划 §5 第 1 条「重启保持」变成一条可自动化的断言 |
| 不引入新组件 | 只用既有 PostgreSQL（`app` schema），符合基座「不引入 Redis/MQ/向量库」的约束 |

### 3.2 负面与代价

| 代价 | 缓解 |
| --- | --- |
| 时钟是**全局**状态，两个浏览器共享同一个演示世界 | 演示流程单操作员；面板上显示 `updated_by` 与业务时间徽标，避免「谁动了时钟」的争论 |
| 测试互相污染（前一个用例把时钟推进了 1 天） | `pg_clean` 夹具每例重建库；每个时钟用例结束时显式 `reset` |
| 定时任务可能被一次性「追回」 | 推进后立即结算到期任务（`run_due`），并按幂等键去重，绝不重复扣款（见设计说明 §6） |
| 多实例缓存不一致窗口 | 缓存 TTL ≤ 1 秒 + 写后主动失效；读路径以库为准 |

### 3.3 约束（对实现者的硬要求）

1. 任何写 `app.sim_clock` 的代码路径必须同时写 `audit.clock_event` 与 `audit.event`，且在**同一事务**里（`append_event` 只 `flush` 不提交）。
2. `version` 每次成功变更 +1；API 返回当前 `version`，用于前端拒绝陈旧响应。
3. `enabled=false` 时 `now()` 与 `real_now()` 必须严格相等（同一调用内只取一次 `real_now()`，避免跨秒抖动导致断言不稳定）。
4. 业务代码不得绕过 `get_clock()`；`tests` 中可用 `use_clock()` 注入替代实现。

## 4. 被否决的备选方案

### 4.1 备选 A：重启回到真实时间（时钟状态只活在内存）

否决理由（四条，任何一条都足以否决）：

1. **演示中断**：一次演示中重启（改配置、切库、误关窗口）后，所有「推进到明天」的演示步骤必须重做，而重做会与已产生的业务数据冲突（例如定时转账已经触发过）。
2. **审计出现断档**：`real_at` 与 `business_at` 的差值会突然归零，事后无法解释「为什么 9:00 的记录排在 10:00 记录之后」，与架构 `:119`「审计同时记录真实记录时间和演示业务时间」的目的直接冲突。
3. **定时任务被错误追回或错误丢弃**：时钟跳回真实时间时，之前「已经到期并结算」的任务会变成「未到期」，而 `app.task.status` 已是 `succeeded`；反向跳变时一批任务会瞬间到期。两种都是账务事故的形状。
4. **直接违反验收**：实施计划 §5 第 1 条要求「`sim_clock` 单行持久化重启保持」。

### 4.2 备选 B：仅内存不持久（进程内单例 + 启动时复位）

否决理由：

1. 与备选 A 的 1/2/3 同构，只是换了实现位置；重启丢失是同一个缺陷。
2. 无法记录 `before`/`after`、`operator`、`version`——而「时钟变更必须审计」是架构 `:126` 的硬约束，内存单例没有可审计的落点。
3. 多进程（`--reload`、`live_server`、并发 worker）下每个进程一份状态，`GET /api/clock` 会返回自相矛盾的答案，前端徽标开始随机跳动。

### 4.3 备选 C：用环境变量/配置文件保存偏移（`BANK_AGENT_CLOCK_OFFSET=+2h`）

额外否决的一条（虽然没人正式提议，但它是「持久化」的诱人近似解）：

1. 改偏移要改文件并重启进程，正好把「重启」变成「必丢现场」的操作，与 D2 的目标相反。
2. 无法在运行期推进（`POST /api/clock/advance` 的核心场景），也无法冻结。
3. 无操作员身份、无时间戳、无版本，审计无从落地。
