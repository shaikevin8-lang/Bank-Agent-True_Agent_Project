## 1. 背景

「让 Agent 现场写一段代码算个数」是本项目最诱人的能力，也是最容易把演示环境一次打穿的能力：R2 要按商户类别算月均、R6 要分摊预算并对账、R3 要试算费率，这些需求天然希望「模型生成代码 → 执行 → 拿结果」。而一旦执行，就意味着我们要在一个**手里有数据库口令、有 Mock 银行写接口、有演示租户数据**的进程旁边，运行一段**内容不可预知**的 Python。

这条路上有五个必须先定死、否则实现必然跑偏的问题：

1. **隔离到底靠哪一层？** 只做静态 AST 检查，等价于「用字符串黑名单防代码执行」——`__subclasses__()` 一条链就能回到 `object` 的完整子类树，再借 `open` 读环境变量；只做容器隔离，等价于「把不可信代码放进一个能联网、有环境变量的箱子里」，逃逸一次就是凭据泄露。**必须三层叠加，且每层都清楚自己拦不住什么**（§3）。
2. **网络到底怎么关？** v1.0 写的是 compose 里 `network_mode: none`，同时又要求 app 侧用 HTTP 调 `http://code-sandbox:8022`——**这两件事在 Docker 里互斥**：`net=none` 的容器没有任何网络接口，连 app 也调不到它（勘误 E5）。这不是措辞问题，是架构矛盾。
3. **`RLIMIT_NPROC` 取几？** v1.0 写 `0`。但 `0` 不是「禁止新建进程」，而是「该 uid 的进程数上限为 0」，解释器自己启动所需的资源分配就会失败（勘误 E9）。写 `0` 的沙箱不是更安全，是**根本起不来**。
4. **它和「业务写沙箱」是什么关系？** 仓库里已经有一个叫「写沙箱」的东西（`R1/tools/transfer_tools.py:_submit_to_sandbox`、礼品 8020/8021），它做的是真实资金写操作的 Mock 回执。如果不在文档里把两者切开，评审会合理怀疑「你们是不是拿业务写沙箱冒充代码沙箱」，实现者也会顺手把两者混成一个适配器。
5. **沙箱挂了怎么办？** 这是最容易被写成「悄悄在本地算一遍」的地方——本地算出来的是**没有经过三层隔离的结果**，它既不是沙箱结果，也不该被标注成沙箱结果。必须有一条明确的降级语义：明确告知、如实标注、绝不自称。

本 ADR 逐条定死这五个问题，并把「已接受的实施修正」（E5、E9）写成可核对的结论，而不是口头共识。

## 2. 决策

### D1 路线 = A（最小真实现）+ B（论证），二者都要

- **A（最小真实现）**：`docker/code-sandbox/` 是**真容器、真 rlimit、真 AST 门**，能跑通 `POST /run` 并对 25 条以上攻击载荷给出 `rejected` / `timeout` / `error`，由 `tests/security/test_sandbox_escape.py` 与 `scripts/verify_code_sandbox.ps1` 出具证据。
- **B（论证）**：本 ADR 的三层能力表（§3）、网络策略（§4）、边界对照（§5）、降级语义（§6）、路线打分（§9）——把「为什么这样就够了、还差什么」讲清楚。
- 理由见开发文档决策 1：B 单独难应对「码实现」类评审（只有文档没有可运行的隔离 = 空谈）；A 单独工作量大且容易停在「能跑」而没有边界论证。**A 提供证据，B 提供边界**。

### D2 三层隔离各自负责一件事，且责任不重叠

| 层 | 一句话职责 | 实现落点 |
| --- | --- | --- |
| 第 1 层 静态 AST 白名单 | **在代码进入解释器之前**否掉「不该出现的东西」：导入、I/O、反射、动态求值、危险语法 | `docker/code-sandbox/ast_guard.py::check_source` / `check_inputs` |
| 第 2 层 进程资源限制 | 代码已经合法，但**行为**（耗时/吃内存/刷输出/生进程）不可接受时，由内核掐断 | `docker/code-sandbox/runner.py`（`resource.setrlimit`）+ 父进程墙钟 `communicate(timeout=)` |
| 第 3 层 容器与编排 | 前两层都被绕过时，**最后一道物理边界**：只读根、无凭据、无出口网络、无 capability、无多余挂载 | `docker-compose.yml` 的 `code-sandbox` 服务 + `sandbox_net` |

三层是**纵深**而非替代：任何一层的失败都不应导致另外两层被放宽。反之，任何一层的收紧也**不得**以牺牲另外两层为代价（例如「把 AST 门放宽一点以支持 import」是不允许的）。

### D3 结果只当「试算」，不得作为金融事实

- 沙箱输出标注 `沙箱计算`；R2 工具回执必须带 `note: "试算结果，非收益承诺"`；降级时标注 `标准统计`。
- 沙箱结果**不得**写入任何资金类事实表、不得作为转账/申购/冻结的金额来源；它只进「分析/展示」通道。理由：沙箱结果的可信度上限是「一段白名单代码 + 64 KB 输出门」，不足以承担账务责任。

### D4 网络：`internal: true` 内部网络 + 不发布宿主端口（E5）

- 沙箱加入 compose 内部网络 `sandbox_net`，`driver: bridge` + `internal: true`：**没有默认网关、没有出口 NAT**，容器只能与本 compose 项目内的其他服务（即 `app`）互访。
- **不写 `ports:`** —— 宿主拿不到 8022，外部与宿主浏览器都进不来。
- `network_mode: none` **仅**用于离线负向测试变体（验证「完全无网卡时会话也起得来」），不作为常态部署形态。
- 完整论证见 §4。

### D5 `RLIMIT_NPROC = 1`，不是 0（E9）

| 参数 | 取值 | 说明 |
| --- | --- | --- |
| `RLIMIT_CPU` | `5` 秒 | 与墙钟 `wall_ms=5000` 呼应，防止「CPU 型」绕过 I/O 型计时 |
| `RLIMIT_AS` | `mem_mb * 1MB`（默认 256 MB） | 地址空间上限，内存炸弹在此被内核拒 |
| `RLIMIT_FSIZE` | `65536` | 即使有人找到写文件的路子，文件也长不大；与「输出 ≤64 KB」同量级 |
| `RLIMIT_NOFILE` | `32` | 抽掉「开一堆 fd」的放大手法 |
| `RLIMIT_NPROC` | **`1`** | **E9**：`0` 会让解释器自身启动受限报错（沙箱根本起不来），`1` 才表达「除当前进程外不再新建」 |

`resource` 模块在 Windows 上不可用 → 跳过 rlimit，**只靠父进程墙钟**（`runner.py` 的 `--report` 子进程 + `communicate(timeout=)`）。因此跨平台可测，但「内存超限」这一条在 Windows 上退化为 `MemoryError` → `INTERNAL_001`，属已知平台差异（§8 R-4）。

### D6 降级：`DisabledCodeComputeAdapter` + `CodeComputeUnavailable`，绝不自称

- 沙箱不可用（未部署 / `BANK_AGENT_CODE_COMPUTE_MODE=disabled` / 熔断 `open` / 传输超时 / 上游 5xx）时，一律抛 `CodeComputeUnavailable`，向上呈现为：
  - `label = "标准统计"`、`degraded = true`、`message = "自定义统计暂不可用，已切换标准统计"`、`result = None`；
  - `error_code` 至少是 `NOT_READY_001`（未就绪/不可用），并带 `reason ∈ {disabled, transport, upstream_error, circuit_open}`。
- **禁止**在降级路径上用本地 Python 算一遍再把结果标成「沙箱计算」。本地重算既没有三层隔离，也没有 `ast_summary` 与 `metrics` 可核；把它标成沙箱结果等于**伪造安全证据**。
- 用户看到的永远是「哪条路算的」：`沙箱计算` 或 `标准统计`，不允许第三种模糊措辞。
- 详细语义见 §6。

### D7 熔断复用 ADR-005 的 `code_compute` 能力，不新增枚举

- `guarded_run` 第一步就是 `circuit_breaker.require_closed(capability=CAP_CODE_COMPUTE)`；`status == "ok"` → `record_success`，否则 `record_failure`。
- 被熔断时抛 `CodeComputeUnavailable("代码计算能力已熔断，暂时不可用", reason="circuit_open", error_code="NOT_READY_001")`——与 ADR-005 D7 / 勘误 E2「不新增错误码族」一致。
- 因此「沙箱连续算挂三次」会像写能力一样被隔离，且 `GET /health/capabilities` 的 `code_compute_enabled` 如实反映。

### D8 幂等键由服务端兜底生成

- `POST /run` 请求体允许 `idempotency_key`；缺省时**服务端生成** `uuid4().hex` 并回填到响应，调用方据此可复现/对账。
- 同键重复请求返回**首次结果**（进程内 LRU，上限 256 条）。副作用为零，所以幂等在这里的作用是「同样的输入不重复消耗 CPU 与日志」，而不是「防重复扣款」。
- 跨重启不保证：进程内缓存随容器重启清空——这在「零副作用」前提下可接受，与 ADR-005 拒绝「进程内状态作为唯一安全状态源」不矛盾（那里是**安全状态**，这里是**计算缓存**）。

## 3. 三层隔离能力表

> 读法：**「拦住」列**是该层的主要战绩；**「拦不住」列**是必须由下一层兜的部分；**「判据」列**是可以用一条断言验证的东西（对应 `tests/security/test_sandbox_escape.py` 与 `verify_code_sandbox.ps1` 的 checks）。

### 3.1 第 1 层：静态 AST 白名单（`ast_guard.py`）

| 维度 | 内容 |
| --- | --- |
| **拦住** | `Import` / `ImportFrom`（`R10` / `R11`）、`Global`/`Nonlocal`（`R12`/`R13`）、`ClassDef`（`R14`）、`AsyncFunctionDef`（`R15`）、`With`/`AsyncWith`（`R16`）、`Try`/`TryStar`（`R17`）、`Lambda`（`R18`）、`Raise`（`R19`）、`Delete`（`R20`）、`Await`/`AsyncFor`（`R21`）、`Match`（`R22`）、`Yield`/`YieldFrom`（`R23`）；禁用名（`open`/`exec`/`eval`/`compile`/`__import__`/`getattr`/`setattr`/`globals`/`locals`/`vars`/`input`/`exit`/`breakpoint`/`type`/`super`/`object`/`memoryview`/`dir`/`help`/`quit`/`id`/`issubclass`/`hasattr`/`delattr` …，`R05`）；禁用属性（`__class__`/`__bases__`/`__subclasses__`/`__globals__`/`__code__`/`__builtins__`/`mro`/`format`/`__dict__`/`__mro__`/`__getattribute__`/`__reduce__` …，`R06`）；非白名单调用（`R07`）；空源码 `R01`、语法错 `R00` |
| **量化上限** | 源码 ≤ **8192** 字节（`R02`）、AST 节点 ≤ **2000**（`R03`）、语句块嵌套 ≤ **3**（`R04`）、`inputs` ≤ **1 MB**（`R30`）且 ≤ **5000 行**（`R31`）、必须 JSON（`R32`） |
| **拦不住** | ① **语义型资源耗尽**：`while True: pass`、`[0] * 10**8`——语法完全合法；② **合法算子的意外代价**：`sorted(...)` 对极大 list、`range(10**9)` 的惰性但配合 `sum` 变实耗；③ **逻辑错误**：算错、除零、`NoneType` 相加——这些不是安全问题，是用户 bug |
| **判据** | `check_source(code)` 通过 → 返回 `ast_summary{nodes,depth,lines,bytes,calls,names,rule_count=0}`；不通过 → 抛 `AstRejection{rule,reason}`，`runner` 转成 `status="rejected"` / `error_code="VALIDATION_001"` / `detail="<规则号>: <原因>"` |

**白名单调用集**（固定，新增需改契约）：`len sum min max abs round sorted enumerate range zip str int float list dict set tuple bool print datetime`。
**为何是白名单而不是黑名单**：黑名单要求我们穷举 Python 全部逃逸面（`__subclasses__`、`__globals__`、`__reduce__`、`mro`、`__builtins__`…），漏一个就等于没有；白名单只需保证「这 22 个名字 + 表达式语法」是安全的，**未列出即拒绝**，错误方向是「少算」，而不是「被打穿」。

### 3.2 第 2 层：进程资源限制（`runner.py`）

| 维度 | 内容 |
| --- | --- |
| **拦住** | 死循环 → 父进程墙钟 `communicate(timeout=wall_ms/1000)` 到期 `kill()` → `status="timeout"` / `UNKNOWN_RESULT_001`；CPU 型长跑 → `RLIMIT_CPU=5`；内存炸弹 → `RLIMIT_AS=256MB` → `MemoryError` 或被内核杀 → `INTERNAL_001` / `"内存超限（256MB）"`；输出洪水 → `print` 重定向到 `io.StringIO`，累计超 `output_bytes`（默认 64 KB）置 `truncated=True` 并**停止累积**；写文件 → `RLIMIT_FSIZE=65536`；fd 放大 → `RLIMIT_NOFILE=32`；fork 放大 → `RLIMIT_NPROC=1`（**E9**） |
| **执行模型** | 父进程 `subprocess` 重跑自身（`runner.py --report <temp>`），payload 走子进程 stdin，结果 JSON 走**文件**（避免与用户 stdout 混流）；子进程在独立命名空间执行，`__name__="__sandbox__"`，仅注入 `inputs`/`data`/`result`/受限 `datetime` 代理 |
| **拦不住** | ① **父进程自身的资源**：`metrics` 只能事后报告（`ru_maxrss`/`ru_utime`），不是事前隔离；② **Windows 无 `resource`**：内存与 fd 上限退化为「靠 `MemoryError` 与墙钟」（§8 R-4）；③ **算法级慢**：5 秒内合法的 `O(n²)` 在 5000 行输入上依然可能让单次请求吃满 CPU——由容器 `cpus: 0.5` 与熔断计数吸收，而不是靠 rlimit |
| **判据** | `execute()` 返回固定键集；`status ∈ {ok,rejected,timeout,error}`；`metrics.wall_ms` 由父进程计时，`cpu_ms = ru_utime + ru_stime`，`peak_mem_kb = ru_maxrss`（不可用为 `0`）；`timeout` 必带 `error_code=UNKNOWN_RESULT_001` 与 `detail="超时 <wall_ms>ms，进程已终止"` |

### 3.3 第 3 层：容器与编排（compose）

| 手段 | 取值 | 拦的是什么 |
| --- | --- | --- |
| `read_only: true` | 整个根文件系统只读 | 落地任何持久文件（后门、缓存投毒）；根目录写探针 `touch /probe` 必须失败 |
| `tmpfs: ["/tmp:size=8m,noexec,nosuid"]` | 唯一可写点，8 MB、**noexec**、nosuid | 即使写进 `/tmp` 也无法执行；8 MB 上限让「往 /tmp 灌大文件」失效 |
| `environment: []` | **零环境变量注入** | 凭据泄露（数据库 DSN、模型 Key、内网地址）。`/selfcheck.credentials` 断言为 `0` |
| `user: "65534:65534"` | `nobody:nogroup` | root 逃逸后的权限放大；配合 `cap_drop: [ALL]` 与 `no-new-privileges:true`，setuid/提权链断掉 |
| `cap_drop: [ALL]` + `no-new-privileges:true` | 丢弃全部 capability | `mount`/`ptrace`/`raw socket` 一类需要特权的动作 |
| `cpus: 0.5` / `mem_limit: 256m` / `pids_limit: 32` | 资源天花板 | 单容器吃满宿主；`pids_limit` 是 fork 炸弹的容器级兜底（进程级已有 `NPROC=1`） |
| 无 `ports:` + `sandbox_net(internal: true)` | 外部不可达、容器无出口 | 数据外传、反连 C2、拉取远端脚本 |
| 无 volume/无 `docker.sock` 挂载 | `mounts == []`（`/`、`/tmp` 除外） | 通过挂载点读到宿主文件或控制宿主 Docker |
| `EXPOSE 8022` 仅文档用途 | 不 publish | 让人误以为宿主可访问 |

**拦不住 / 残余**：宿主 Docker daemon 被其他路径攻破（超出本 ADR 范围）；内核 0day 逃逸（演示环境的接受风险，见 §8 R-6）；`internal: true` 仍允许**同项目内**服务互访——沙箱可访问 `app:8000` 一类内部端点，因此**sandbox 与 app 之间不存在额外的网络 ACL**，只能靠「沙箱内没有 HTTP 客户端能力（无 `import`）＋结果不含请求凭据」保证不被打成跳板。

## 4. 网络策略（E5 的完整论证）

### 4.1 三个候选与结论

| 候选 | 能否被 app 调用 | 有无外网出口 | 结论 |
| --- | --- | --- | --- |
| `network_mode: none` | **否**（无任何网卡，`http://code-sandbox:8022` 不可解析不可达） | 无 | **不可作常态形态**；仅作离线负向测试变体 |
| 默认 bridge（不 publish 端口） | 是 | **有**（默认网关 + NAT） | 否决：沙箱能反连外网，等于给了外传通道 |
| **`sandbox_net` + `internal: true`** | **是**（同项目服务名可解析） | **无**（无默认网关、无出口 NAT） | **采用** |

`internal: true` 的语义正是「这个网络只对内，不设外部出口」：Docker 不会给它默认路由，容器发出的外部连接在 `connect()` 阶段失败。它同时满足两条上位要求——「app 要能 HTTP 调 8022」与「沙箱不得有真实出站」。

### 4.2 落地约束（逐条可断言）

| 约束 | 写法 | 断言方式 |
| --- | --- | --- |
| 内部网络 | `networks: { sandbox_net: { driver: bridge, internal: true } }` | `docker network inspect <proj>_sandbox_net` → `Internal: true` |
| 不发布端口 | 服务内**不写** `ports:`；保留了 `EXPOSE 8022` 只是镜像文档 | `docker port bank-agent-code-sandbox` 空输出 |
| 无外网 | 同 `internal: true` | 容器内 `python -c "urllib.request.urlopen('https://example.com')"` **必须抛异常**（`verify_code_sandbox.ps1` 的 `no-external-network` check） |
| 无凭据 | `environment: []` | `/selfcheck` → `credentials == 0` |
| 无多余挂载 | 不写 `volumes:` | `/selfcheck` → `mounts == []` |
| 零出口的服务端自证 | `app.py` 启动时采样：`network`=能否建立外部 TCP（期望 `False`），`credentials`=环境变量个数（期望 `0`），`mounts`=`/proc/mounts` 中除 `/`、`/tmp` 之外的挂载点（期望 `[]`） | `GET /selfcheck` 三键同时成立 |

> `network_mode: none` 的存续价值：它是**负向测试的对照臂**——证明「即便完全没有网卡，沙箱也能完成一次计算」，从而把 E5 的矛盾从「不可行」变成「有一臂专门验证不可行方案的表现」。它出现在测试说明里，不出现在常态部署里。

## 5. 与「业务写沙箱」的边界对照表

> 这两个名字都以「沙箱」结尾，但在系统里的位置、职责、可信度**完全不同**。混用是评审最容易抓的点。

| 维度 | 业务写沙箱（银行 8020 / 礼品 8021，`R1/tools/transfer_tools.py:_submit_to_sandbox` 等） | 代码沙箱（8022，本 ADR） |
| --- | --- | --- |
| 解决什么问题 | 演示环境下「钱怎么写出去」——把真实写接口替换成 Mock，产出**回执**（成功/失败/未知 + 交易号） | 「模型写的这段代码能不能安全地跑」——受控计算 |
| 处理的对象 | 资金与权益的**写请求**（转账、卡状态、申购、冻结、礼品兑换） | **一段 Python 源码**（≤8 KB） |
| 是否有副作用 | **有**（在 Mock 账本里真实改变余额与状态，只是不触及真实银行） | **零**（不写数据库、不写文件、不联网、不调金融工具） |
| 凭据 | 需要 Mock Core 的认证与租户上下文 | **零凭据**（`environment: []`，`credentials == 0`） |
| 幂等的作用 | 防**重复扣款/重复发货**——同 `idempotency_key` 必须只有一次副作用 | 防**重复消耗 CPU**——同键返回首次结果，无副作用可言 |
| 输出是什么 | 业务回执（结构化，可入账） | JSON 值 + `ast_summary` + `metrics`（**仅供展示/试算**） |
| 能否作为金融事实 | **能**（在演示范围内作为「已发生」的事实，进账务与审计） | **绝对不能**（`note: "试算结果，非收益承诺"`；不进资金事实表） |
| 归属门禁 | HITL 三道门 + `write:transfer` 等 5 项写能力熔断 | 仅 `code_compute` 一项能力熔断；**不经 HITL 建案**（纯计算无需人工批） |
| 失败后的用户可见语义 | 交易失败/待核（`UNKNOWN_RESULT_001` → 先查后决） | 「已切换标准统计」降级（`NOT_READY_001`，`degraded=true`） |
| 端口 / 网络 | 8020 / 8021，Mock Core 由 app 进程内调用 | 8022，`sandbox_net` 内部网络、不发布宿主端口 |
| 一句话 | **钱的沙箱**：隔离的是「真实金融机构」 | **代码的沙箱**：隔离的是「不可信代码」 |

**反向约束**（必须写清，否则会有人「顺手复用」）：

1. 代码沙箱**不得**被用来发起任何金融写操作——它连 HTTP 客户端都没有（无 `import`），物理上做不到。
2. 业务写沙箱**不得**被用来执行模型生成的代码——它是 `httpx` Mock，不提供任何代码执行能力与资源上限。
3. 两者**不得**合并成一个适配器或一个能力枚举：`code_compute` 与 `write:*` 在 ADR-005 中是不同 capability，熔断与复位互不影响。

## 6. 降级策略

### 6.1 三种不可用与统一的对外语义

| 触发 | 适配器状态 | `reason` | 抛出的异常 / 呈现 | 页面/回执 |
| --- | --- | --- | --- | --- |
| 沙箱未部署、`BANK_AGENT_CODE_COMPUTE_MODE=disabled` | `DisabledCodeComputeAdapter`（`name="disabled"`，`available()=False`） | `disabled` | `CodeComputeUnavailable(DEGRADED_MESSAGE, reason="disabled")` | `label="标准统计"`、`degraded=true`、`result=None` |
| 连接失败 / 超时（8 秒） | `HttpCodeComputeAdapter`（`name="http"`） | `transport` | `CodeComputeUnavailable("代码沙箱不可达，已切换标准统计", reason="transport")` | 同上 |
| 上游 HTTP 5xx | 同上 | `upstream_error` | `CodeComputeUnavailable(..., reason="upstream_error")` | 同上 |
| `code_compute` 能力被熔断（ADR-005 `open`/`half_open` 已取用） | 任意适配器（先被门禁拦） | `circuit_open` | `CodeComputeUnavailable("代码计算能力已熔断，暂时不可用", reason="circuit_open", error_code="NOT_READY_001")` | 同上 |

统一提示语常量：`DEGRADED_MESSAGE = "自定义统计暂不可用，已切换标准统计"`（不写「系统错误」「未知异常」，因为**它不是错误，是一次已完成的降级**）。

### 6.2 `compute_category_monthly` 的降级返回形状（固定）

```python
{"ok": False, "label": "标准统计", "degraded": True,
 "message": "自定义统计暂不可用，已切换标准统计",
 "result": None, "sandbox": None, "error_code": "NOT_READY_001"}
```

- 成功时：`{"ok": True, "label": "沙箱计算", "degraded": False, "message": "", "result": {...}, "sandbox": {image,network,credentials}, "error_code": None}`。
- **`label` 只有两个取值**：`沙箱计算` / `标准统计`。任何「结果来自本地重算却标 `沙箱计算`」的实现都是缺陷（§2 D6）。

### 6.3 三条硬约束

1. **绝不用本地计算冒充沙箱结果**。`guarded_run` 内**没有**任何 fallback 分支；本地重算只在 `compute_category_monthly` 之外的「标准统计」路径里发生，且必须打 `label="标准统计"`。
2. **降级不吞异常语义**：`CodeComputeUnavailable` 原样上抛，由 R2 工具层转成结构化回执（`ok=False`），而不是在适配器里 catch 后返回假数据。
3. **降级要可观测**：`/health/capabilities.code_compute_enabled=false` 由 `/health/capabilities` 与运维接口观测（前端降级横幅已于 2026-11-01 移除）；沙箱连续失败达阈值后熔断接管（§2 D7），避免每条请求都白等 8 秒超时。

### 6.4 适配器契约（调用方视角）

| 符号 | 语义 |
| --- | --- |
| `CodeComputeAdapter`（Protocol） | `name: str` / `available() -> bool` / `selfcheck() -> dict` / `run(*, code, purpose, inputs, limits, idempotency_key) -> dict` |
| `HttpCodeComputeAdapter` | `name="http"`；`base_url` 取 `BANK_AGENT_CODE_SANDBOX_URL`，缺省 `http://code-sandbox:8022`；`POST {base}/run`、`GET {base}/selfcheck`；`httpx.Client`，`timeout_s=8.0` |
| `DisabledCodeComputeAdapter` | `name="disabled"`；`available() -> False`；`run()` 直接抛 `CodeComputeUnavailable(DEGRADED_MESSAGE, reason="disabled")` |
| `get_adapter` / `configure_adapter` / `reset_adapter` | 单例注入点；`BANK_AGENT_CODE_COMPUTE_MODE ∈ auto\|http\|disabled`（缺省 `auto`：能连就 http，否则 disabled） |
| `code_compute_enabled() -> bool` | 供 `/health/capabilities` 使用；异常一律 `False`（**fail-closed**，与 ADR-005 D6 同向） |
| `guarded_run(...)` | 熔断门禁 → 适配器 `available()` → `adapter.run()` → 成功/失败记账 → 返回响应并追加 `{"sandbox_label": "沙箱计算"}` |
| `compute_category_monthly(inputs, ...)` | 生成「按 `category` 分组算月均/全期均值」的沙箱代码（`amount_fen` 整数运算），返回 §6.2 形状 |

## 7. 错误码映射表

四个码全部来自**基座冻结清单**，本阶段**不新增码族**（勘误 E2）。`/run` 的业务状态以 body 的 `status` + `error_code` 表达，调用方**只读 body**，不依赖 HTTP 状态码分支（HTTP 层由 `app.py` 决定，不在本 ADR 冻结范围内）。

| 错误码 | 语义 | 生产者 | body `status` | `detail` 形状（固定前缀） | 调用方动作 | 熔断计数 |
| --- | --- | --- | --- | --- | --- | --- |
| `VALIDATION_001` | 输入被拒（策略层拦截，不是故障） | `ast_guard` → `runner` → `app.py` | `rejected` | `"<规则号>: <原因>"`，如 `"R10_IMPORT: 禁止导入语句"`、`"R02_TOO_LARGE: 源码 9200 字节超过 8192"`、`"R40_PURPOSE: 未知用途"` | **不重试**（内容问题，重试同样被拒）；把规则号回显给作者 | **不计**（这是门在工作） |
| `NOT_READY_001` | 能力未就绪 / 已熔断 / 已禁用 | `code_compute.guarded_run`、熔断门禁 | —（不出现在 `/run` 响应，出现在适配器异常与降级回执） | `"自定义统计暂不可用，已切换标准统计"`（disabled/transport/upstream）/`"代码计算能力已熔断，暂时不可用"`（circuit_open） | 走「标准统计」降级路径，标注 `标准统计` | **不计**（避免降级风暴把能力锁死） |
| `UNKNOWN_RESULT_001` | 结果未知（超时被杀，无法断言是否算完） | `runner` 父进程 | `timeout` | `"超时 <wall_ms>ms，进程已终止"` | 可**有限重试 1 次**（或降级），不得当作「算出来了」使用 | **计一次失败** |
| `INTERNAL_001` | 执行期故障（内存超限 / 用户代码抛异常 / 结果不可序列化） | `runner` 子进程 | `error` | `"内存超限（256MB）"` / `"<异常类型>: <异常信息>"`（**不泄栈**）/ `"结果不可 JSON 序列化"` | 同输入重试无意义；降级或提示改写代码 | **计一次失败** |

补充口径：

- **`rejected` 不熔断**：策略拒绝说明防线在工作（攻击者在撞门），把它计成失败会让攻击者用 22 条负向载荷把能力锁死——那是「自伤型 DoS」。
- **`timeout` 计失败**：超时说明代码已经跑进「资源不可控」区，连续三次意味着沙箱对当前负载不健康。
- **降级不计失败**：沙箱根本没被调用（`disabled`）或连不上（`transport`）时，`record_failure` 会让一次网络抖动引发全能力锁定；这类情况只记日志与 `code_compute_enabled=false`，把「沙箱不健康」交给部署侧发现。（`guarded_run` 契约里 `status != "ok"` 才记账，而传输异常会**先抛出**，不会走到记账行——契约与本文一致。）
- **幂等回放**：同 `idempotency_key` 命中缓存时，**原样返回首次结果**（含原 `error_code`），不重新计失败、不重新执行。

## 8. 后果与风险

### 8.1 正面

| 收益 | 说明 |
| --- | --- |
| 「码实现」有实物证据 | 真容器 + 真 rlimit + 真 AST 门，25 条以上负向用例可跑、可截屏、可给评委复现 |
| 纵深不重叠 | 静态层管「不该出现」，进程层管「行为失控」，容器层管「万一穿透」；任一层的绕过假设都不会让整体失守 |
| 边界可陈述 | 与业务写沙箱的对照表（§5）把「钱的沙箱 / 代码的沙箱」彻底切分，杜绝「拿 Mock 冒充」的质疑 |
| 降级诚实 | 三态标注（`沙箱计算`/`标准统计`/失败）+ 明确提示语，用户永远知道结果的来源 |
| 与熔断天然契合 | `code_compute` 早在 ADR-005 预置；沙箱不健康时自动隔离，页面仍可看标准统计 |
| 零凭据可断言 | `/selfcheck` 三键（`network/credentials/mounts`）是**机器可验**的安全声明，不是文档承诺 |

### 8.2 负面与代价

| 代价 | 缓解 |
| --- | --- |
| 白名单很窄，用户会觉得「什么都写不了」 | 这是设计意图：22 个调用 + 表达式语法足够覆盖「分组/均值/分箱/分摊/试算」；不够用就走标准统计，而不是放宽白名单 |
| 5 秒 / 256 MB / 64 KB 有硬上限 | 参数可下调不可上调（`limits` 越界截到上限）；超限语义明确（`timeout` / `memory` / `truncated`），不是静默截断 |
| 冷启动要构建镜像（`python:3.12-slim` + pip） | `docker compose up -d --build` 后镜像本地缓存；`verify_code_sandbox.ps1` 在 docker 不可用时输出 `skipped` 而不是假装通过 |
| Windows 无 `resource`，内存上限退化为 `MemoryError` | 明确写进契约与本文（R-4）；CI/演示以 Docker 为准 |
| 多一层网络与容器，故障面变大 | 降级路径（§6）覆盖全部不可用形态，且不计熔断失败 |

### 8.3 两条已接受的实施修正（必须写进文档，不要再犯）

| 编号 | v1.0 写法 | 修正为 | 为什么 |
| --- | --- | --- | --- |
| **E5** | compose 里 `network_mode: none`，同时要求 app 用 HTTP 调 `http://code-sandbox:8022` | **`sandbox_net` + `internal: true`**（无默认网关、无出口 NAT）+ **不发布宿主端口**；`network_mode: none` 仅作离线负向测试变体 | `net=none` 的容器没有任何网络接口，app 也调不到它——「无外网」和「可被 app 调用」在 `none` 下互斥，是**架构矛盾**，不是措辞问题。`internal: true` 才是同时满足两者且不给外传通道的唯一解（§4） |
| **E9** | `RLIMIT_NPROC=0` | **`RLIMIT_NPROC=1`** | `0` 不是「禁止新建进程」，而是「该 uid 进程数上限为 0」，解释器自身启动所需的资源分配即失败——沙箱根本起不来。`1` 表达「除当前进程外不再新建」 |

### 8.4 风险与未决项

| 编号 | 风险 / 未决 | 描述 | 处理 |
| --- | --- | --- | --- |
| R-1 | AST 白名单可能被语义绕过 | 白名单只覆盖「名字与语法」，理论上仍可能通过合法算子构造超长计算（`sum(range(10**8))`） | 第 2 层 rlimit + 墙钟 + 容器 `cpus: 0.5` 兜底；红队清单持续补载荷（DOC-TEST-001 §3） |
| R-2 | `internal: true` 仍允许同项目内互访 | 沙箱理论上可访问 `app:8000`，成为「内网跳板」 | 沙箱内无 HTTP 客户端能力（无 `import`，`socket` 不可得）；结果不含请求凭据；若将来放宽 import，必须先引入网络 ACL 并回改本 ADR |
| R-3 | 四个错误码是否都在基座 `:142` 冻结清单内 | 勘误 E2 只点名了 `NOT_READY_001` / `UNKNOWN_RESULT_001` | 收尾时逐码核对基座清单；若 `VALIDATION_001` / `INTERNAL_001` 不在清单内，**回写基座契约**而不是就地自造码族 |
| R-4 | Windows 无 `resource` 导致内存上限不可强制 | 本地跑 `runner.execute` 时内存炸弹只会在 `MemoryError` 时暴露 | 契约明确「不可用时跳过，仅靠父进程墙钟」；容器内为权威口径；`test_sandbox_isolation.py` 无 docker 时 `pytest.skip` |
| R-5 | 幂等缓存是进程内 LRU（256 条） | 容器重启即丢，超出 256 条被淘汰 | 零副作用前提下可接受（§2 D8）；不复用为安全状态源（区别于 ADR-005） |
| R-6 | 内核 / 容器运行时 0day 逃逸 | `internal: true` + `read_only` + `cap_drop: ALL` 不能防内核级逃逸 | 演示环境接受风险并在安全自评报告中登记（§8 三层隔离对照表的「残余风险」列）；生产化需 gVisor/Kata 等第二层隔离运行时 |
| R-7 | `/selfcheck` 的 `credentials` 口径 | 镜像自身 `ENV`（如 `PYTHONDONTWRITEBYTECODE`/`PYTHONUNBUFFERED`/`PATH`）会计入环境变量个数，导致 `credentials != 0` | 这是**实现侧待确认项**：若确实非 0，应在 `app.py` 里按「非镜像自带的环境变量」口径统计，或把镜像 `ENV` 收敛到最小集；`verify_code_sandbox.ps1` 对 `os.environ` 采用「近似为空」判定（键名白名单 + 不含凭据关键字）并在 `detail` 里回显实际键，便于定位 |

## 9. 替代方案对比（A / B 打分）

评分口径：1 = 很差，5 = 很好；权重为该维度对「评审可验证性 + 安全事故成本」的综合重要度。

| 维度 | 权重 | **A 最小真实现** | 打分 | **B 仅论证** | 打分 | A+B 组合 | 打分 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 可运行证据（评委能自己跑） | 0.30 | 真容器 + 25 条负向 + `verify` 脚本 JSON | 5 | 无，只能读文档 | 1 | 有容器也有边界陈述 | 5 |
| 隔离强度（三层是否齐） | 0.20 | 三层齐全（AST/rlimit/容器） | 5 | 纸面三层，无断言 | 2 | 三层 + 每层判据 | 5 |
| 实施成本（4 人日内可否完成） | 0.15 | 偏紧：Dockerfile/app/runner/ast_guard/适配器/测试 | 2 | 极低 | 5 | 紧但可行（契约已冻结） | 3 |
| 降级与可运维性 | 0.15 | 需自建适配器与降级（已冻结） | 3 | 只能写「不可用则提示」 | 2 | 明确 `DisabledCodeComputeAdapter` + 提示语 | 5 |
| 与既有体系契合（熔断/审计/健康度） | 0.10 | 复用 `code_compute` 能力与 `/health/capabilities` | 4 | 无法验证契合度 | 1 | 完全契合（§2 D7） | 5 |
| 误用风险（结果被当金融事实） | 0.10 | 需显式标注口径 | 4 | 无实现即无约束 | 1 | 标注 + 不进事实表 + `note` 提示 | 5 |
| **加权合计** | 1.00 | — | **3.95** | — | **1.85** | — | **4.65** |

**结论**：采用 **A+B 组合**（加权 4.65）。A 提供「能跑的证据」，B 提供「拦不住什么」的边界声明——单独任何一项都不足以同时满足「码实现」评审与安全工作量的现实约束。

**被否决的备选**：

| 备选 | 否决理由 |
| --- | --- |
| C：不做沙箱，只靠提示词约束「不要写危险代码」 | 提示词不是安全边界（架构 §10 同一取向：禁止以前端/提示词过滤替代沙箱）；一句 `__import__('os')` 即穿透 |
| D：用业务写沙箱（8020/8021）代跑计算 | 它是 `httpx` Mock，没有代码执行能力、没有 rlimit、没有 AST 门；且「钱的沙箱」一旦被当成「代码执行器」，回执的可信度与账务责任被污染（§5） |
| E：只做容器、不做 AST 与 rlimit | 容器内仍可 `while True` 吃满 CPU、可读 `/proc`、可借 `__subclasses__` 探测；容器是最后一道，不该是唯一一道 |
| F：只做 AST，不建容器 | AST 一旦被语义绕过（R-1）就无兜底；且无 `read_only`/零凭据/无出口网络，凭据与内网暴露面全开 |

## 10. 验证方式

### 10.1 一条命令出结论（推荐）

```powershell
# 仓库根执行；-KeepUp 便于连续复跑（默认 false 会在结束时 docker compose down）
pwsh -NoProfile -ExecutionPolicy Bypass -File scripts\verify_code_sandbox.ps1
```

stdout **只有**一个 JSON：

```json
{"passed":9,"failed":0,"skipped":[],"checks":[{"name":"selfcheck-network","ok":true,"detail":"network=false"}],"docker":true}
```

`docker` 不可用时脚本不报错，输出 `{"passed":0,"failed":0,"skipped":["docker-unavailable"],...,"docker":false}` 并 `exit 0`（沙箱不可测不等于代码有问题）。

### 10.2 手工四步

```powershell
# 1) 起沙箱（仅内部网络，不发布宿主端口）
docker compose up -d --build code-sandbox

# 2) 容器内自证：network=false / credentials=0 / mounts=[]
docker compose exec -T code-sandbox `
  python -c "import urllib.request;print(urllib.request.urlopen('http://127.0.0.1:8022/selfcheck').read().decode())"

# 3) 健康与能力键（app 侧）
curl.exe -s http://127.0.0.1:8000/health/capabilities

# 4) 正/负向用例
python -m pytest tests/security/test_sandbox_escape.py tests/contract/test_code_compute.py -q
```
