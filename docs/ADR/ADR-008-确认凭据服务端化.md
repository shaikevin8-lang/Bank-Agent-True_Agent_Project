## 1. 背景

阶段 3 之前，「用户已确认」这件事由**被审对象自己声明**。`hitl._user_confirmation()` 直接读模型给出的工具参数：

```python
confirmed = arguments.get("confirmed") is True
mfa_code = str(arguments.get("mfa_code") or "")
mfa_ok = (not rule.requires_mfa) or (confirmed and len(mfa_code) == 6 and mfa_code.isdigit())
```

由此产生的 D04 漏洞是一条完整的绕过链：

1. **确认事实由被审对象自证**：模型只要在参数里写 `confirmed=true`，`_check_user_confirmation()` 就认为用户确认过；而模型的参数本身来自可被注入的上下文。
2. **验证码退化为「6 位数字格式检查」**：`mfa_code` 只要是 6 位数字即算通过，`123456`、`000000` 与真实下发的码没有区别。
3. **无主体绑定**：凭据里没有 `tenant/user/session`，A 用户的确认可被 B 用户或另一个会话拿去用。
4. **无一次性**：同一组参数可以反复通过同一道门，重放旧确认等于无限次授权。
5. **重放路径自己补确认**：`hitl_replay.py` 的 `_REPLAY_EXTRA` 与 `_FALLBACK_MFA` 会 `setdefault("confirmed", True)`——存档参数里没有确认也能执行。

结论：红色门禁此前保护的是「模型有没有写 `true`」，不是「用户有没有确认」。本 ADR 把确认从**模型可写的参数**搬到**服务端持有的凭据**。

## 2. 决策

### D1 确认链路全服务端：click → request → MFA → grant → consume

前端点击确认不再直接带布尔值，而是走五个服务端环节：

```text
点击确认 ──▶ POST /api/v1/confirm/request  （服务端建 request，绑定 tenant/user/session/tool/fingerprint/risk_level，TTL 180s）
输入 6 位码 ──▶ POST /api/v1/confirm/mfa    （校验存在/主体/锁定/过期/未用/次数，通过后签发 grant）
门禁放行  ──▶ confirm.consume_grant(...)    （存在/未撤销/未用过/未过期/主体/工具/指纹/熔断，全通过才置 used_at）
```

红色（`requires_mfa=True`）走完三步；黄色/绿色建请求后**服务端直接签发**（`status=issued`），前端不需要输码，但仍然拿到一个可校验的 `grant_id`，不再有「前端说确认了就确认了」的分支。

### D2 门禁只读 `grant_id`，模型传来的确认字段一律丢弃

`hitl._user_confirmation(tool_name, rule, arguments)` 的唯一输入是 `arguments["confirmation_grant_id"]`；为空时回落到服务端会话态 `confirm.session_grant(tool_name, args, session_id, ...)`（同会话 + 同工具 + 同指纹 + 未用 + 未过期）。模型传 `confirmed` / `mfa_code` 时：

- 由 `param_guard.sanitize()` **原地删除**并审计 `security.param_injection_attempt`；
- `_user_confirmation` 再记一条 `security.prompt_ignored`（`deprecated_param_ignored`）；
- 证据字典返回 `confirmed=False, mfa_ok=False, source="model_arguments_ignored"`，**绝不**因模型写了 `confirmed=True` 而放行。

全仓库**唯一**写 `confirmed=True` 的地方是 `hitl.intercept()` 在「凭据已消费」之后向调用方字典注入的服务端哨兵（`confirmed=True` + `mfa_code="000000"`，工具侧只校验格式），并审计 `confirm.grant_injected`。

### D3 凭据是不透明随机令牌，库里只存哈希

`grant` 的对外价值是 `grant_id`；真正的令牌是 32 字节 `secrets.token_urlsafe(32)`，服务端只存 `sha256` 十六进制。6 位验证码同理：只存 `sha256("<request_id>:<code>")`，明文码仅在演示面板端点 `demo_sms()` 出现一次。比对一律 `hmac.compare_digest`（常数时间），不给逐位试探留时间侧信道。

### D4 主体 + 工具 + 参数指纹三重绑定

`consume_grant()` 要求 `tenant_id` / `user_id` / `session_id` 与签发时一致（否则 `SubjectMismatch` → `AUTHZ_001`）、`tool_name` 一致、`args_fingerprint == hitl.fingerprint(tool_name, args)`（否则 `FingerprintMismatch` → `VALIDATION_001`）。为了让「确认后重试」不被自身参数击穿，`confirmation_grant_id` 被加入 `hitl.VOLATILE_ARG_KEYS`，不参与指纹计算。

### D5 一次性 + TTL + 重放不续签

`consume_grant()` 用 `Store.consume_grant(grant_id, used_at=...)` 的**原子 CAS** 置 `used_at`（`expected_status` 语义同样用于 `update_request`）：并发下只有一个调用能成功，第二个拿到 `GrantReused` → `CONFLICT_001`。`grant` TTL 120 秒、`request` TTL 180 秒。`hitl_replay.replay()` 在执行前核对 `confirmation.grant_id` 的状态，已用/过期/撤销即抛 `ReplayUnavailable("确认凭据已失效，请用户重新确认")`，**不自动续签**——续签等于让「恢复执行」变成一条免确认通道。

## 3. 状态机与参数

```text
request:  pending ──码对──▶ used            （红色：先 pending 后签发）
          pending ──错 3 次──▶ locked
          pending/used ──TTL──▶ expired
          pending ──用户取消──▶ revoked
          （非红色：建请求即 issued，无 pending 阶段）
grant:    issued ──consume 成功──▶ used
          issued ──TTL 180→120s 到期──▶ expired（惰性判定，不改行）
          issued ──用户取消──▶ revoked
```

| 参数 | 值 | 来源 / 理由 |
| --- | --- | --- |
| `REQUEST_TTL_SECONDS` | 180 | 契约值；覆盖「收到卡片 → 找手机 → 输码」的演示节奏 |
| `GRANT_TTL_SECONDS` | 120 | 凭据只保证「刚确认完那一下」，不保证「明天还能用」 |
| `MFA_MAX_ATTEMPTS` | 3 | 错 3 次锁定，挡字典穷举（10⁶ 空间下 3 次机会无实用价值） |
| 验证码 | 6 位十进制，`secrets.randbelow(1_000_000)` 补零 | 与演示短信面板的展示长度一致 |
| 令牌 | `secrets.token_urlsafe(32)`（43 字符 base64url） | `param_guard` 的格式白名单按此长度校验 |
| `STORE_ENV` | `BANK_AGENT_CONFIRM_STORE ∈ memory\|sql`（缺省 `sql`） | 单测用 `memory`，演示与集成用 PG |

## 4. 备选方案与为何否决

| 备选 | 否决理由 |
| --- | --- |
| A. 前端持有布尔值（`confirmed=true` 由页面提交） | 前端是**不可信输入源**：改一行 JS、直接打接口即可伪造；且无法防重放（同一请求可无限重发）。这与「服务端不信任前端」的既有口径（人工介入设计 §5.1）直接冲突 |
| B. 模型持有确认码（模型把用户口述的码写进参数） | 码一旦进入模型上下文就等于进入提示词，可被注入读取、被日志落盘、被下一轮对话复述；等于把 MFA 降级成「模型记得的一个字符串」。故 `param_guard` 把 `mfa_code`/`otp`/`pin` 全部列为敏感键丢弃 |
| C. JWT 自签（服务端签一个含 `confirmed:true` 的 token 给前端） | 签名只证明**签发者**，不证明**一次性**与**主体当前性**：token 在 TTL 内可无限重放，撤销要额外维护黑名单；而「已用」状态本来就必须落库（审计与重放核对都要读）。多一层密码学，换不来少一行状态记录 |
| D. 复用人工案件 `POST /decision` 的 `approve` | `approve` 是**人工复核**闸门，与用户确认是两个独立事实（FR-COM-003：人工通过不能代替用户确认）。合并会让「复核员批准」意外满足「用户确认」，是需求明令禁止的降级 |

## 5. 后果

### 5.1 正面

| 收益 | 说明 |
| --- | --- |
| 确认不可伪造 | 攻击者能改的只有 `grant_id`；改一个字节就是 `GrantInvalid`/`FingerprintMismatch`，无中间态 |
| 可审计 | `confirm.requested` / `mfa_failed` / `grant_issued` / `grant_consumed` / `grant_rejected` / `grant_injected` / `request_cancelled` 七个动作覆盖全链路，一次确认可按序重演 |
| 与熔断、越权正交 | `consume_grant` 末尾复用 `hitl.breaker_gate(tool_name)`，凭据有效但能力被熔断时仍拒绝（`GrantInvalid`） |
| 测试可离线 | `BANK_AGENT_CONFIRM_STORE=memory` 下无 PostgreSQL 依赖，红线用例是纯函数级断言 |

### 5.2 代价与缓解

| 代价 | 缓解 |
| --- | --- |
| 确认多一次往返（request → mfa → 执行） | 非红色路径不输码（建请求即签发）；红色路径多一次 POST 换来的是可验证的一次性授权，值得 |
| 前端要维护「请求中」中间态 | 服务端兜底 `session_grant()`：前端丢了 `grant_id` 也能凭会话态匹配到同指纹的未用凭据，不会把用户卡死在重试上 |
| 多两张表 + 清理任务 | `purge_expired(older_than_seconds=3600)` 与启动时清理；`expires_at` 上有索引，清理是范围删除 |
| 存储双实现（`MemoryStore`/`SqlStore`） | 接口是 `Store` Protocol，测试与演示各取一份；行为差异由 `test_confirm_api.py` 覆盖 |
| `confirmation_grant_id` 进 `VOLATILE_ARG_KEYS` 后，指纹不再覆盖该字段 | 该字段本身由 D2/D4 校验（主体 + 工具 + 指纹 + 状态），不需要进指纹；反之若进指纹，「确认后重试」必然指纹不符 |

## 6. 安全属性

| 属性 | 机制 | 失效面（被击穿时会发生什么） |
| --- | --- | --- |
| **不可伪造** | 令牌 32 字节随机 + 只存哈希 + 常数时间比对 | 库被读走也拿不到令牌；伪造需猜中 2²⁵⁶ |
| **一次性** | `consume_grant` 原子 CAS 置 `used_at` | 并发重放只有一个成功，另一个 `GrantReused` |
| **主体绑定** | `tenant_id`/`user_id`/`session_id` 三重比对 | 跨用户冒用直接 `SubjectMismatch` → `AUTHZ_001`；跨会话同用户也拒绝（防「借用别人的确认」） |
| **指纹绑定** | `hitl.fingerprint(tool_name, args)` 与签发时比对 | 确认 500 元后改成 5 万执行 → `FingerprintMismatch` → `VALIDATION_001` |
| **TTL** | request 180s / grant 120s，惰性判定 | 过期即 `GrantInvalid`，不续签、不宽限 |
| **可审计** | 七个 `confirm.*` 动作 + `security.*` 动作 | 失败一律审计 `confirm.grant_rejected`（带 reason），不静默丢弃 |
| **fail-closed** | 无凭据/凭据异常 → `confirmed=False`；`param_guard` 解码异常 → 判注入 | 任何「判断不了」都落到「不放行」，不落到「默认确认」 |
