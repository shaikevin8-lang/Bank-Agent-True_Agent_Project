## 0. 文档定位与使用规则

本文件是 AI Banking Agent 的产品需求冻结基线，也是 Vibe Coding 的约束输入。它冻结产品范围、业务规则、安全不变量、Agent 职责边界和可观察验收结果，回答“系统必须做什么、何时可以做、何时必须拒绝、完成时用户应看到什么”。

架构图、接口字段、工具 Schema、数据库表、完整状态机、Prompt 文本、模型参数、重试/超时参数、测试用例、部署运维和性能压测由配套开发设计、测试和部署文档承接。实现可以调整这些细节，但不得削弱本文件的 P0 要求，也不得通过代码、Prompt 或配置绕过本文件。

当文档发生冲突时，优先级为：已确认的《比赛作品要求》 > 本文件“不可妥协基线” > 本文件其他 P0 > P1/P2。任何影响范围、权限、安全、确认或验收口径的变更，必须形成新版本并同步受影响的验收项。

## 1. 不可妥协基线

以下规则是所有场景、所有 Agent、所有工具和所有界面的共同硬约束：

1. 首版只使用中文文本、CNY、Asia/Shanghai、一个专用演示租户、合成数据和银行/礼品沙箱；不得接入真实资金、真实客户数据或真实第三方下单。
2. 关键字段缺失、冲突或多义时必须澄清，不能猜测金额、收款人、时间、账户、地址、商品或风险属性。
3. 余额、流水、产品、卡、订阅、订单和执行结果以沙箱工具返回的事实为准；模型记忆不能替代实时事实。
4. 只读查询可以在权限校验后自动完成；任何资金、授权、卡状态、预算预留、订单或可复用自动化任务写入，都必须经过显式确认，并按风险等级追加模拟 MFA 或人工复核。
5. 模型只能理解、规划和解释，不能直接访问银行写接口，不能绕过权限、风控、确认、审计或沙箱边界。
6. 所有写操作必须可幂等、可追踪、不可因重复提交产生第二次副作用；未知结果必须先查询原操作，禁止盲目重放。
7. 失败、处理中、部分完成、结果未知和人工处理必须如实展示，不得以“成功”掩盖异常；无法安全自动恢复时转人工。
8. 越权、提示注入、伪造确认、金额/收款人篡改、审计不可用或安全门不可用时，写操作必须拒绝或暂停并记录审计。
9. 六个场景及其下列全部子能力均为本项目 P0；每项都必须有独立路由、独立验收和可重复演示。
10. 需求未定义的金融写行为不得自行新增；新能力进入 P1/P2 或新版本需求后再实现。

## 2. 比赛范围与项目范围

比赛要求覆盖六个核心场景、自然语言理解与任务执行、绿色/黄色/红色权限分级、幻觉和提示注入防护、关键操作审计、异常熔断、受限代码沙箱、复杂任务的中断/回退/人工接管，以及作品资料、答辩和演示视频。本项目将下表全部子能力冻结为 P0，这些是项目选定的实现范围，不表述为比赛逐字列出的独立指标。

来源边界：六个核心场景、权限分级、幻觉/提示注入防护、关键审计、异常熔断、受限代码沙箱和复杂任务接管属于比赛要求；幂等、未知结果先查询、最小人工复核、租户隔离、脱敏和预算/账务对账属于本项目为保证沙箱安全和可验收性增加的 P0 基线。两类要求在 P0 中同等有效，但不能把项目扩展项误称为比赛逐字硬指标。

| 场景 | P0 子能力 |
|---|---|
| R1 智能转账 | 按姓名转账、按手机号转账、按历史备注转账、定时转账、拆分 AA 收款 |
| R2 账单分析 | 消费分类统计、异常交易识别、月度账单报告、年度账单报告 |
| R3 理财操作 | 风险评估、产品推荐与对比、一键申购、一键赎回 |
| R4 卡片管理 | 虚拟/演示卡申请、额度调整、交易限制与解锁、卡片挂失/冻结 |
| R5 订阅/代扣管理 | 自动识别订阅扣费、续费提醒、一键取消订阅/代扣 |
| R6 跨场景联动 | 生日场景：预算预留、定时触发、鲜花和蛋糕礼品沙箱订单 |

比赛红色示例中的密码修改不属于六场景，本版本不提供密码修改能力，也不注册对应可执行工具；后续需要时按新需求增加。

### 2.1 P0、P1、P2 边界

**P0**：六场景全部子能力、统一对话闭环、权限分级、确认、幂等、审计、提示注入防护、受限代码沙箱、最小人工复核、未知结果处理、沙箱隔离、演示时钟和数据重置。

**P1**：外部 IM 渠道、在线 RAG 和复杂知识更新、图片/OCR、多级或批量人工审批、复杂通知偏好与长期记忆、增强可观测性和离线评测。P1 不得成为 P0 的隐含前置条件。

**P2**：真实第三方适配器、多模型路由、本地离线推理、更多生活事件和个性化财务洞察。仍只允许在沙箱中演示。

首版交付形态为可通过 GitHub 获取并在本地启动的 Web 应用，用户通过浏览器网页使用中文聊天入口。应保留统一会话、认证、渠道和审计边界，为后续接入 IM 等其他渠道留出位置；外部 IM 不属于 P0，不因未接入而降低 P0。

## 3. 产品目标、非目标与用户

### 3.1 产品目标

用户可以用中文自然语言完成六类银行任务；系统能在信息不足时追问，在多步骤任务中形成可解释计划，并在沙箱中安全执行。用户、风控人员和评委可以看到事实依据、风险决策、确认记录、工具轨迹和最终回执。

### 3.2 非目标

本版本不实现真实支付、真实 KYC/AML、征信、真实理财交易、真实信用审批、真实礼品配送、真实商户解约、真实密码或 PIN 修改。大模型不替代银行核心账务、适当性或风控最终决定，也不向用户展示模型内部推理原文。

### 3.3 角色

| 角色 | P0 能力边界 |
|---|---|
| 普通用户 | 查看本人数据，创建草稿，确认或取消本人任务，查看结果和审计摘要 |
| 风控审核员 | 处理分配给自己的单案件：通过、拒绝或补件并填写理由；不能代替用户确认 |
| 管理员/运营演示角色 | 管理演示配置、重置数据、查看脱敏轨迹和案件；不能审批或代替用户执行金融写入 |

所有会话、任务、工具调用和审计事件必须绑定演示租户和资源所有者。AA 参与人只能查看和处理自己的份额；礼品地址、人工案件和其他敏感对象按最小必要范围可见。

## 4. 通用交互与任务要求

### 4.1 统一用户旅程

用户输入 → 识别领域、动作、对象和约束 → 澄清缺失/冲突字段 → 生成计划摘要 → 规则与风险预检 → 只读执行或生成不可执行草稿 → 对有副作用的动作展示确认 → 执行沙箱写操作 → 返回事实回执、状态和下一步。

页面布局由设计文档决定，但用户必须能够理解：当前任务做什么、依据什么、是否会产生副作用、是否需要确认/人工处理、现在是什么状态、失败或未知时下一步是什么。

### 4.2 最小用户可见状态

需求层只冻结以下用户可理解阶段：

| 阶段 | 含义 |
|---|---|
| 需澄清/草稿 | 信息不足或已形成不可执行方案 |
| 待确认 | 已展示完整事实和风险，等待用户明确确认 |
| 已安排/已暂停 | 定时或跨场景任务已登记，尚未到执行节点，或被用户暂停 |
| 处理中 | 已进入沙箱或等待外部/人工结果 |
| 成功 | 沙箱明确受理/完成，回执与事实一致 |
| 失败/已取消/已过期 | 没有产生未核对副作用，给出原因和重新发起方式 |
| 结果未知/人工处理 | 先查询原操作或交由人工处理，不提供直接重试 |

完整状态名、迁移条件、并发控制和补偿步骤属于设计与测试文档。任何实现都必须保证上述状态之间的语义不被混淆。

### 4.3 澄清、确认与恢复

- 每轮优先询问一个最能推动任务的问题；关键字段未齐不得生成可执行写计划。
- 多候选收款人、多个付款账户、AA 余数分配、订阅取消层级、生日年份/地址/预算等必须让用户明确选择。
- 确认内容必须包含对象、金额或范围、账户/卡尾号、时间、费用/风险和预计结果；修改关键事实后原确认失效并重新评估。
- 普通文本“好的”不能代替高风险确认；高风险动作必须使用明确确认控件并完成模拟 MFA。
- 依赖超时、审批不可用、审计不可用、模型不可用或风控不确定时，按 fail-closed 处理。只读可降级为规则/模板；写操作不得自动执行。
- 定时任务触发前、跨场景订单最终提交前必须重查易变事实。执行中的任务只能按当前沙箱边界取消、补偿或转人工。

## 5. Agent 与 LangGraph 需求边界

### 5.1 技术约束

整体任务编排使用 LangGraph。该约束只用于保证任务可暂停、可恢复、可观察和可重规划；节点命名、图结构、模型供应商、存储方式和具体代码由开发设计文档决定。

### 5.2 业务 Agent 职责

每个 P0 子能力应能够被独立路由、独立验收和独立停用。转账（姓名/手机号/备注/定时/AA）、账单、理财、卡片、订阅和生日工作流分别负责自己的业务规则；跨场景编排只负责组合依赖，不得替代领域规则。公共编排能力负责路由、澄清、计划协调和升级，但不能越过领域 Agent 的权限边界直接写入银行。

需求不冻结 Agent 数量、Supervisor/Risk/Audit 等实现角色清单。若开发将这些职责拆成多个 Agent，必须满足以下协作契约：

1. 输入、输出、风险判断、确认要求和执行结果均使用结构化业务对象，不能只传自由文本。
2. 每个 Agent 只处理已授权领域和资源，不得读取或修改其他领域的受限数据，不得自行新增工具或确认。
3. 所有副作用统一经过公共权限、风控、确认、幂等和审计安全门；子 Agent 不能绕过安全门。
4. Agent 无法判断、发现事实冲突、执行失败或结果未知时，必须报告澄清、暂停、人工处理或未知结果，不能伪造成功。

### 5.3 自主规划的产品要求

系统应根据用户约束动态组合多个领域、安排依赖并在约束变化或工具不可用时重新规划；不能只播放固定脚本。计划对用户展示摘要、步骤依赖、风险和需要确认的节点，对运营人员保留可回放轨迹。具体评测方法和计划数据结构由测试/设计文档承接。

## 6. 统一功能需求

### FR-COM-001 对话与会话

支持中文多轮文本对话、会话恢复、上下文引用、任务取消和任务结果查询。会话失效、跨租户访问或用户资源不匹配时，必须重新认证或拒绝，不得沿用旧确认。

### FR-COM-002 结构化理解与计划

每次业务请求至少产出：领域/动作、已识别实体、缺失或歧义字段、用户约束、计划摘要、风险/确认建议、事实依据和任务追踪标识。结构化结果校验失败时不得调用写工具，应澄清或失败并审计。

### FR-COM-003 确认与人工复核

有副作用的动作必须有可回看的确认记录；高风险动作还需模拟 MFA。命中人工策略时创建单案件、单审核员的人工复核，审核员只能通过、拒绝或补件并填写理由。人工通过不能代替用户确认，事实变化后必须重新评估。复杂批量分配、多级审批和复杂 SLA 属于 P1。

### FR-COM-004 任务、通知与审计

用户可查看本人定时任务、生日工作流、提醒、确认和结果。每次 Agent 运行、关键工具调用、权限/风控决定、人工处理、状态变化和失败恢复都必须可追溯、不可静默删除；运营只能查看脱敏轨迹。

### FR-COM-005 统一安全执行

工具必须白名单化、参数可校验、检查资源归属和权限，并区分只读、草稿和写入。写入必须使用服务端生成的幂等控制和沙箱标识；模型不得动态执行函数名、拼接 SQL/Shell 或把自然语言直接当金融指令。若运行受控计算代码，只能在无网络、无凭据、资源受限的代码沙箱中运行，代码输出还必须经过校验。

## 7. 六场景功能需求

### R1 智能转账

**FR-TR-001 收款人解析**：支持姓名、手机号和本人历史备注。手机号、账号和候选信息脱敏；无候选时说明无法匹配；多候选时展示匹配依据并由用户选择；备注只能查询本人历史记录。

**FR-TR-002 立即转账**：用户明确金额、付款账户、收款人和币种后，系统查询余额、限额、账户/收款人状态和风险，先生成草稿，确认后在沙箱执行。金额必须大于零，首版只支持 CNY；余额不足、账户冻结、越权、风控命中或事实变化时拒绝。成功只在沙箱明确受理/入账后展示，并返回脱敏回执。

**FR-TR-003 定时转账**：保存日期、时刻和时区，用户可在触发前查看、修改、暂停或取消。触发时重新检查余额、限额、账户、收款人和风险；不自动改期。定时任务本身是可复用授权，创建或修改需确认，触发时不重复确认但仍须通过最终安全门。

**FR-TR-004 AA 收款**：支持总金额、参与人、均分/指定分摊和截止日期。金额以分计算，余数和发起人是否承担份额必须明确；只生成站内请求，不自动扣参与人账户。每位参与人独立确认/付款，只能看到自己的份额；支持部分付款、逾期、取消和沙箱退款/冲正，未知或退款失败转人工。

转账日累计超过比赛约定的 1,000 元按高风险处理，不能通过拆单规避。具体限额、风险规则和运行参数由策略/设计文档承接，但只能收紧本基线。

### R2 账单分析

**FR-BILL-001 消费分类统计**：支持月、年和指定区间，展示分类、总额、趋势和主要商户。统计只使用已入账流水，明确纳入/排除口径和更新时间；分类合计应与流水对账。用户可修正分类，修正需记录并只影响本人偏好。

**FR-BILL-002 异常交易识别**：识别疑似高金额、重复扣费、异常时间、陌生商户、新设备或异常地点等模式，但只有流水存在相应证据才能展示原因。使用“疑似异常/建议核实”，不得直接断言欺诈；用户可标记误报或发起处理。

**FR-BILL-003 月度/年度报告**：生成月度和年度报告，包含区间、更新时间、收支总览、分类、趋势、主要商户、异常摘要和数据说明；导出需授权并脱敏。

### R3 理财操作

**FR-WEALTH-001 风险评估**：推荐或申购前必须确认风险测评有效；缺失、过期或答案冲突时先补测。输出风险等级、有效期和适当性限制，不推断未授权敏感属性。

**FR-WEALTH-002 产品推荐与对比**：按资金、期限、流动性和风险偏好筛选产品，展示风险等级、期限、起购金额、流动性、费用、适配理由、风险提示和来源。不得承诺收益、隐瞒费用或把不适配/过期产品作为可购买项。

**FR-WEALTH-003 申购与赎回**：支持对适配产品建立申购或赎回草稿，明确金额/份额、全部/部分、到账预期和风险揭示，确认后在沙箱执行。最终提交前重查测评、产品状态、报价/净值、余额或持仓；不适配、余额/持仓不足、停售、冷静期或交易时段不符时阻断。订单部分完成、结算失败或未知时查询原订单并补偿/转人工，禁止盲重放。

### R4 卡片管理

**FR-CARD-001 卡申请**：支持虚拟/演示卡申请，收集最小合成 KYC，展示条件和处理状态，不能承诺必然通过。

**FR-CARD-002 额度调整**：先明确临时/永久、币种、渠道和有效期，校验状态、KYC、限额和风险。申请提交与额度生效必须分别反馈；超限或高风险转人工/拒绝。

**FR-CARD-003 交易限制与解锁**：支持线上、境外、取现等限制及撤销。限制设置需确认；解锁属于高风险，需身份校验、模拟 MFA 和必要人工复核。卡号只显示后四位。

**FR-CARD-004 挂失与冻结**：用户必须选择临时冻结或永久挂失。确认后执行沙箱冻结并返回回执；永久挂失不可逆，补卡另建请求；重复点击不得产生重复副作用。

### R5 订阅/代扣管理

**FR-SUB-001 订阅识别**：从流水识别疑似周期扣费，展示商户、周期、金额、最近/预计扣费、证据和置信度；推测日期必须标注为估算，用户可纠正。

**FR-SUB-002 续费提醒**：支持设置、修改、暂停和取消扣费前的站内提醒；提醒不触发扣款。

**FR-SUB-003 取消订阅/代扣**：必须区分撤销银行代扣授权和提交商户解约申请，先查询授权/合约及在途扣款，再展示影响、费用和预计生效时间。用户选择层级并确认后才调用沙箱；两类请求分别返回结果，失败或未知先查询/转人工，不能笼统显示“订阅已取消”。银行授权撤销成功后关联提醒和自动化任务应停止或失效。

### R6 跨场景联动

**FR-WF-001 生日预算与礼品工作流**：支持生日日期/时区、预算账户、生日月预留 1,000 元活期资金、生日前两天触发、鲜花和蛋糕两条礼品订单以及用户最终确认。

1. 缺少年份、地址、预算、账户或商品偏好时澄清；“先给我看方案”只能生成不产生副作用的方案预览。
2. 用户单独确认后才预留预算。生日当月按 1,000 元预留活期资金；预算预留是沙箱可用余额占用，不是转账或对外支付；生效前再次检查余额和已有预留。
3. 工作流须有清晰依赖：触发 → 商品检索 → 预算/库存/配送检查 → 方案 → 用户最终确认 → 礼品沙箱下单。价格、库存和配送在最终确认前重查，变化时重新确认。
4. 礼品总预算不得超过用户设定的上限（演示脚本使用 600 元），预留、已承诺、已释放和剩余金额必须可对账。部分订单成功时按订单行展示，不得全量报成功。
5. 用户可暂停、取消或修改未执行部分；修改账户、金额、日期、地址或商品后，相关确认失效。订单/预留未知、释放失败或补偿失败时先查询并转人工。

## 8. 权限、风险与安全需求

### 8.1 绿色/黄色/红色分级

| 比赛级别 | 需求层含义 | P0 控制 |
|---|---|---|
| 绿色 | 查询、分析、报告和不产生副作用的草稿 | 登录、资源权限、事实依据和脱敏后可自动完成 |
| 黄色 | 低风险可逆或小额业务写入 | 显式确认、幂等、审计；策略需要时升级 |
| 红色 | 高金额、资金/授权/卡状态/外部订单等高风险写入 | 规则检查、用户确认、模拟 MFA，命中策略时人工复核；不得自动放行 |

具体业务映射必须保持清晰：小额转账、预算预留和限制设置至少为黄色；超过 1,000 元的转账、理财申赎、额度调整、解锁、挂失、代扣撤销和礼品下单至少为红色。

### 8.2 三道安全门

**输入门**：认证、会话、租户/资源归属、敏感信息最小化、重放控制和提示注入检测。要求泄露提示词、绕过权限、修改工具参数或伪造确认的输入必须阻断并审计。

**工具门**：白名单工具、参数校验、权限/限额/状态检查、幂等、审批、沙箱和审计。风控、审批或审计不可用时，写操作 fail-closed。

**输出门**：事实来源校验、敏感字段掩码、风险说明、错误/未知状态校验和禁止收益承诺。只有沙箱明确结果才能展示成功。

### 8.3 数据与审计

全部演示数据为合成或脱敏数据。完整账号、手机号、身份证、卡号、密码、OTP、生物信息和地址不得无必要进入模型上下文、日志或截图。外部模型必须通过模型网关处理脱敏内容，供应商输出视为不可信输入，仍需经过结构化、权限和事实校验。

关键操作审计至少能关联用户、租户、任务、计划版本、工具、风险决定、确认/审批、结果和时间；原始审计不可由运营或管理员静默修改/删除。审计不可用时禁止有副作用的写操作。

### 8.4 异常、熔断与人工处理

连续写失败、提示注入、越权、审计失败、未知结果或补偿失败时，应暂停相关写能力并通知用户；具体触发次数和冷却时间属于策略/设计参数。未知结果必须查询原操作，不能直接重试；无法安全确定时创建人工案件。人工审核只提供最小闭环：单案件、通过/拒绝/补件、理由和审计。

## 9. 数据和实现边界

需求只冻结以下业务对象及关系：客户/会话、账户/收款人/流水、计划/任务、确认/人工案件、风险测评/产品/订单、卡片服务、订阅/提醒、AA 请求/份额、生日工作流/预算/礼品订单、知识引用和审计事件。对象的字段、表结构、API、事件和状态编码由设计文档定义。

所有金融事实以 Mock Core Banking 为唯一写入边界；余额、预留、订单、转账和退款必须可核对。金额使用可精确计算的方式，首版 CNY；时间必须带时区。实现不得创建需求中未定义的真实金融能力。

## 10. 用户体验要求

用户不需要学习命令即可完成任务。确认卡、状态、风险拦截、失败原因、数据更新时间和下一步动作必须清晰可见；高风险操作不能隐藏在普通聊天文本中。界面布局、组件、路由和视觉规范由设计文档决定，但不得出现“草稿显示成已执行”“未知显示成成功”或敏感信息泄露。

## 11. P0 验收基线

详细测试数据、边界组合、评测集规模和执行步骤由测试文档承接。本文件只冻结每项 P0 的最小可观察结果：

| 验收组 | 最小成功证据 |
|---|---|
| 转账 | 姓名、手机号、备注均能正确匹配或澄清；立即/定时转账确认后产生一次沙箱结果；AA 生成独立份额且不自动扣款 |
| 账单 | 月/年统计与流水一致；异常有真实证据和疑似表述；报告可查看并脱敏导出 |
| 理财 | 完成有效测评；推荐有费用、风险、适配理由和来源；申购/赎回确认后返回沙箱订单或明确阻断 |
| 卡片 | 卡申请、额度申请、限制/解锁、冻结均有独立请求和状态；高风险动作有确认/MFA |
| 订阅 | 识别有周期证据；提醒不扣款；银行授权撤销与商户解约分开反馈 |
| 生日联动 | 先预览后预留；按依赖触发鲜花和蛋糕方案；最终确认后下单；预算可对账，失败/未知可处理 |
| 自主规划 | 同一请求组合多个领域时能澄清、形成依赖计划并留下可回放轨迹；约束变化后能重规划或升级 |
| 通用安全 | 查询可自动完成；写操作确认前零执行；越权/提示注入被阻断；相同请求不重复产生副作用；未知不盲重放；审计可回放；受限代码沙箱阻止网络、凭据和宿主访问；连续失败触发写能力熔断并转人工 |

每个验收组都必须覆盖四类路径：成功、缺失/歧义、权限/风控阻断、失败/未知/取消。发布阻断条件包括：任何 P0 子能力缺少成功路径；确认前发生高风险写入；越权成功；重复幂等产生第二次副作用；未知被盲重放；页面成功与沙箱事实不一致；关键审计缺失；真实数据、密钥或真实金融接口进入提交包。

## 12. 开发、测试与交付文档边界

开发设计文档负责架构、LangGraph 图、Agent/工具契约、数据结构、接口、完整状态机和部署方式；测试文档负责测试用例、评测集、红队样例、故障注入和性能指标；部署运维文档负责启动、配置、监控、备份、回滚和环境管理。本需求文档只要求这些文档与本基线一致，不在此重复实现细节。

P0 交付仍需包含比赛要求的源代码、README、部署说明、测试用例、系统架构图、核心算法说明、安全自评报告、答辩 PPT（不超过 10 分钟）和演示视频（不超过 5 分钟），以及可重置的合成演示环境。

## 13. 需求追踪与变更

六个场景的每项子能力必须有对应需求 ID、成功验收、澄清/阻断验收和失败/未知验收。需求、设计、测试和演示脚本之间通过同一需求 ID 追踪。需求 ID、P0/P1 边界、风险分级、确认条件或验收口径发生变化时，必须更新版本、变更说明和受影响文档；未经变更不得用实现细节替换本基线。
