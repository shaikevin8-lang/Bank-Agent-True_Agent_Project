## 1. 文档定位

本文件把《AI_Banking_Agent_项目基座文档》转化为搭建范围清单，帮助团队先完成一个可启动、可验证、可扩展且不会产生真实金融副作用的项目底座。《AI_Banking_Agent_项目基座文档》是基座实现的冻结执行依据；本引导文档用于归纳和规划，不能覆盖其技术版本、端口、命令、安全边界和验收口径。若发现两份文档冲突，应先按基座文档实施并记录待修订项，不得自行选择其中一套实现。

它只说明基座要准备什么、各部分的边界是什么、先后顺序如何安排，不替代需求、总架构、接口契约、数据库设计、Agent 设计和测试文档。涉及业务范围、风险等级、确认条件、审计口径或真实/沙箱边界时，以上游文档为准，并通过 ADR 和文档版本变更同步。

基座完成不代表六个场景已经完成。基座阶段只提供公共能力、占位交互、合成事实、隔离沙箱和验证入口，所有金融写能力默认关闭。

## 2. 基座建设目标与范围

基座应让新开发者从干净环境完成以下事情：

- 启动 Web、API、worker、PostgreSQL 和本地 Mock/沙箱服务。
- 使用演示身份建立和结束认证会话，创建对话会话，查看任务占位、确认摘要占位和状态时间线。
- 执行迁移、确定性种子、健康检查、测试和受保护的演示重置。
- 验证认证、租户/资源所有者隔离、三道安全门、幂等、审计、脱敏和 fail-closed 行为。
- 在不接入真实模型、真实银行、真实客户或真实第三方的前提下，为后续六场景接入提供稳定端口。

基座不应提前承担以下内容：六场景完整业务流程、完整业务状态机、生产身份认证、真实支付或交易、真实 KYC/AML、真实礼品订单、真实密码/PIN 修改、复杂审批系统、RAG/向量库、OCR、消息队列和长期语义记忆。

## 5. 工程骨架与依赖边界

仓库应预先建立以下稳定边界：

```text
apps/web          React 中文 Web 入口
apps/api          FastAPI HTTP 入口和上下文装配
apps/worker       异步任务、定时触发和恢复入口
packages/application     用例和业务应用入口
packages/orchestration   LangGraph 编排适配
packages/domain          领域服务接口、值对象和规则端口
packages/security_gates  输入门、工具门、输出门
packages/adapters        静态白名单适配器
packages/persistence     仓储、checkpoint、幂等和审计实现
packages/sandbox         代码、金融写、礼品写沙箱客户端/运行时
packages/observability   审计、日志、指标、追踪和熔断状态
packages/prompts         版本化 Prompt 和消息模板
packages/shared          公共类型、错误和基础值对象
contracts                OpenAPI、JSON Schema、事件契约
migrations                Alembic 迁移
seeds                     base/demo 确定性种子
tests                     unit/contract/integration/security/e2e
deploy                   Compose、容器和健康探针
config                   local/test/demo 配置模板与 schema
scripts                  bootstrap、dev、data、test、demo、verify
docs                     架构、契约、数据库、Agent、测试和变更记录
```

依赖方向固定为“入口 → 应用/编排 → 领域 → 安全门 → 静态适配器 → 事实源/沙箱”。前端不得连接数据库或工具；Agent/编排不得直接调用写端；领域层不得导入具体适配器；持久化实现只能通过端口被应用调用。使用 import-linter 和架构测试把这些边界纳入 CI。

## 6. 前端基座需要准备什么

前端只做用户交互和状态呈现，不能成为权限、事实或副作用的控制点。

### 6.1 页面与基础交互

- 中文登录/演示身份入口，并持续显示当前为演示环境。
- 会话列表、会话创建/结束、消息输入和多轮对话容器。
- 任务列表、任务详情、状态时间线和事实/更新时间占位区域。
- 确认卡、风险提示、人工处理、结果未知和取消/恢复的占位状态。
- 加载、空数据、失效会话、校验失败、权限不足、服务不可用和超时页面。
- 统一的响应式布局、键盘可用性、错误提示和脱敏展示规则。

基座阶段的确认卡只允许展示不可执行 fixture 或“能力尚未接入”，不得出现可触发金融写入的按钮或伪成功结果。

### 6.2 前端基础模块

- 路由与访问控制壳：只负责页面入口和会话存在性检查。
- API client：统一 base URL、Cookie、超时、请求 ID、错误映射和 RFC 9457 问题详情处理。
- 状态层：区分认证会话、对话会话、任务状态、网络状态和 UI 状态。
- 领域无关组件：状态标签、时间线、确认卡、风险提示、脱敏文本、空态和重试引导。
- 类型生成或共享契约消费：前端类型必须来自 `contracts/`，避免手写出与 API 不一致的对象。
- 浏览器安全边界：不在 localStorage、URL 或 bundle 中保存银行凭据、工具凭据和长期 token。

### 6.3 前端验收关注点

前端至少要能证明：未登录不能访问受保护页面；会话失效后回到登录；状态不会把处理中、未知或人工待办渲染成成功；跨主体对象由后端拒绝；浏览器网络请求不含内部 Mock、沙箱、秘密或完整敏感标识。

## 7. 后端基座需要准备什么

### 7.1 HTTP/API 层

基座先实现边界稳定的占位 API：

- `POST /api/v1/auth/session`、`DELETE /api/v1/auth/session`：建立和结束演示认证会话。
- `POST /api/v1/sessions`、`GET /api/v1/sessions`、`GET /api/v1/sessions/{session_id}`、`DELETE /api/v1/sessions/{session_id}`：对话会话生命周期。
- `POST /api/v1/sessions/{session_id}/messages`：输入门保护的占位消息接收。
- `GET /api/v1/tasks`、`GET /api/v1/tasks/{task_id}`：本人任务查询。
- `GET /api/v1/tasks/{task_id}/timeline`、`GET /api/v1/tasks/{task_id}/confirmation`：只读状态和确认摘要。
- `/health/live`、`/health/ready`、`/health/capabilities`、`/health/circuit-breaker`：按能力报告服务状态。

所有 API 应统一版本前缀、请求 ID/trace ID、时间格式、RFC 9457 `application/problem+json` 错误、脱敏规则和状态语义；列表接口按契约定义一致的分页方式。客户端提交的 tenant、owner、role、risk、confirmation 或 MFA 字段不得作为授权依据。

认证使用 Cookie 时，应明确本地开发与后续部署的同源/跨源策略；需要跨源携带 Cookie 时，必须使用明确的 CORS 来源 allowlist，并定义写请求的 CSRF/Origin 校验，不能使用允许任意来源的凭据式 CORS 配置。HTTPS 部署时 Cookie 应按基座要求启用 `Secure`。

### 7.2 应用与领域入口

- 应用服务是唯一的业务用例入口，负责组装上下文、调用端口、事务边界和状态更新。
- 领域包先提供公共值对象、状态枚举、领域端口和安全相关结果类型，六场景规则随后分别接入。
- 编排层只负责路由、澄清、计划、暂停、恢复和重规划，不承载领域规则。
- worker 负责异步恢复、定时任务和操作查询，但所有副作用仍必须重新经过安全门。
- 每个未来 P0 场景应能独立路由、停用、测试和观察。

### 7.3 认证、授权和上下文

服务端每次请求都构造并校验不可变的 `Principal`、`TenantContext`、`ResourceOwnerContext`、`SessionId`、`TraceId` 和 `RequestId`。默认演示租户为 `demo-tenant`，角色为 `user`、`reviewer`、`operator`；演示身份只在 local/demo 开启。

会话存 PostgreSQL，浏览器使用 HttpOnly、SameSite=Lax Cookie；绝对过期 8 小时、空闲过期 30 分钟。operator 不能代用户确认或审批，reviewer 只能处理分配给自己的案件。

## 8. 数据库基座需要准备什么

数据库文档应把“基座通用数据”与“六场景业务数据”分开，先让前者稳定，再由 DOC-DB-001 扩展业务实体。

### 8.1 数据库分层与共通原则

- PostgreSQL 采用 `app` 和 `audit` 两个 schema；业务查询不得直接读取审计表替代业务事实。
- 所有可见资源带租户和资源所有者归属；关键查询按服务端上下文重新授权。
- 金额使用精确数值或最小货币单位，首版只支持 CNY；时间带时区，业务基线为 Asia/Shanghai。
- 迁移由 Alembic 显式执行，应用启动只检查版本和漂移，不静默改表。
- 种子具版本、稳定业务键、确定性 ID、哈希清单和幂等重跑能力。
- 关键唯一性、外键、状态约束、索引、并发版本和删除/保留策略在数据库层表达，不只依靠代码。

### 8.2 `app` schema 的基座持久化范围

基座先实现后续开发确实依赖的通用持久化能力，不把下游业务模型提前固化为基座表。基座阶段需要支持：

- 演示租户、主体/角色映射、资源所有者关系和认证会话。
- 对话会话及必要的消息顺序；消息内容须先经过输入门脱敏，并按契约确定保留范围，不额外保留未经处理的原始敏感输入。
- 最小任务摘要、用户可见状态/时间线，以及任务与 LangGraph checkpoint、图运行和 Prompt 版本之间的关联。
- 服务端生成的幂等标识，以及供操作查询/回执核对测试使用的关联记录。
- 基座审计记录和迁移版本/执行结果。

基座不要求建立完整 DAG 步骤、业务确认/MFA 生命周期、人工案件流程、场景级策略历史或任务重试队列等物理模型。占位 API、契约类型或安全门测试夹具可以先定义相应引用，但实际表结构和状态机由 DOC-DB-001、DOC-CONTRACT-001、DOC-AGENT-001 承接。数据库字段、表拆分和索引在 DOC-DB-001 评审后冻结；并发版本字段按实际并发更新需求确定，不作为所有表的统一模板。

### 8.3 `audit` schema 的基座对象

审计至少要记录请求、主体、租户、任务、图运行、门禁决定、权限/风险结果、确认/MFA、人工处理、工具调用、沙箱回执、状态变化、失败恢复、重置和熔断事件；基座阶段只记录实际发生的事件，未实现的业务事件由下游场景接入。审计记录追加写入并保留 365 天，按基座文档使用 SHA-256 链形成完整性校验证据；链头保护、归档校验及其威胁边界由 DOC-DB-001/部署文档明确，不能仅凭同库哈希链宣称具备防篡改存储。归档和保留期处理必须留下审计事件。

审计记录不能包含原始凭据、OTP、完整卡号、完整账号或不必要的敏感文本；审计不可用时，有副作用的写路径必须拒绝。

### 8.4 为六场景预留的扩展边界

后续数据库设计需要承接账户/收款人/流水、计划/任务、风险测评/产品/订单、卡片、订阅/提醒、AA 请求/份额、生日预算/礼品订单、知识引用等对象。基座只提供归属、任务、幂等、事实回执、审计和迁移能力，不在本阶段猜测场景字段或创建未被需求定义的金融能力。

## 9. Agent、模型和任务编排基座

- LangGraph 是唯一任务编排框架，PostgreSQL 保存 checkpoint。
- 图状态只保存路由、澄清、计划、门禁结果和任务引用，不保存余额、流水、产品、卡或订单等账务事实。
- 每次恢复、定时触发和最终提交前都重新查询 Mock Core Banking/沙箱事实并重新过安全门。
- `task_id`、`graph_run_id` 和 `idempotency_key` 贯穿任务、checkpoint、工具调用和沙箱操作。
- Prompt 存在 `packages/prompts/*.yaml`，固定记录 ID、版本、输入/输出 Schema 和 SHA-256；版本写入运行记录。
- 模型调用经过统一网关、最小上下文、输入脱敏、结构化输出校验、超时和成本统计；模型输出永远是不可信候选。
- 模型不得授权、确认、执行 MFA、修改审计、决定风险最终结果或动态增加工具。
- 超时、断连和未知结果先查询原操作；任务取消不代表副作用已经取消。

基座只需验证编排容器、结构化模型响应、checkpoint、恢复和安全拒绝，不需要在此阶段完成六场景 Agent。

## 10. 安全执行链与隔离组件

### 10.1 三道安全门

- 输入门：认证、租户/所有者、字段完整性、敏感信息最小化、重放控制、提示注入和越权检查。
- 工具门：静态白名单、参数和资源校验、绿/黄/红风险策略、确认/MFA/人工条件、幂等、写前事实复查、熔断和审计。
- 输出门：返回值来源、Schema、金额/对象/状态一致性、部分完成/未知处理和敏感字段掩码。

任何门、审计、风控、幂等存储、事实源或确认状态不可用时，写路径 fail-closed。基座的 `writes_enabled` 保持 `false`，不注册场景业务写处理器；沙箱写入仅用于受控协议测试夹具，不能作为可供用户触发的业务能力。

### 10.2 必要适配器和沙箱

- Mock Core Banking：提供合成账户、流水、产品、卡、授权和操作查询事实，是金融事实唯一来源。
- 银行写沙箱：定义固定写请求、操作查询和模拟回执协议，不产生真实资金副作用；基座阶段只通过隔离测试夹具验证协议，不开放用户可调用的场景写处理器。
- 礼品写沙箱：提供合成商品、库存、配送和订单回执协议，不连接真实商户或配送；基座阶段只验证隔离协议，不开放用户可调用的场景写处理器。
- 代码沙箱：独立容器、无网络、无凭据、无宿主挂载，并有 CPU、内存、时长、输入/输出限制和输出校验。
- 模型网关、身份适配器、时钟适配器、审计、指标、熔断和通知端口。

适配器采用静态注册清单，禁止模型或用户提交任意函数名、URL、SQL、Shell 或自然语言写命令。

## 11. 环境、配置、部署和秘密

至少准备 `local`、`test`、`demo` 三套配置、数据库目标、数据目录、秘密命名空间和端点 allowlist。三套环境不能共享可写数据或重置目标。

固定服务端口为 Web 5173、API 8000、PostgreSQL 5432、模型 Mock 8010、Core Banking Mock 8011、银行写沙箱 8020、礼品写沙箱 8021、代码沙箱 8022；内部服务不得直接暴露给浏览器。

配置启动前校验环境名、Schema、必填项、迁移版本和端点；未知字段、未知环境、非 allowlist 地址和试图切换真实端点的配置必须失败。秘密只在运行时注入，不写入仓库、命令行、README、日志、模型上下文、构建产物或截图。

应提供 Windows 和 Unix 等价入口：`bootstrap`、`dev up/down/logs`、`test`、`demo up`、`data migrate/seed/reset`、`verify`。脚本必须显式显示目标环境，并保护 demo 不被误重置。

## 12. 可观测性和运维准备

- liveness 只检查进程存活；readiness 按 `read_only`、`orchestration`、`sandbox_write` 区分能力，不把进程存活误当成可写。
- 结构化日志使用脱敏字段；全链路共享 trace ID、request ID、task ID、graph run ID 和幂等键。
- 指标至少覆盖任务完成/阻断/人工/未知率、澄清与确认轮次、工具拒绝/重复率、模型/沙箱/审计可用性、未知积压、对账差异、熔断状态和模型成本。
- LangGraph 轨迹、工具调用、门禁决定、回执和恢复过程可回放；运营只能看最小必要的脱敏视图。
- 写能力熔断、审计不可用、未知结果积压、人工案件积压和对账异常具备可查询状态和告警入口。
- README 说明启动、停止、日志、健康检查、重置、默认演示身份、能力边界和常见故障。

## 13. 测试、CI 与质量门禁

基座阶段至少建立以下测试层：

- 单元测试：配置、值对象、状态映射、脱敏、幂等和安全门决策。
- 契约测试：OpenAPI/JSON Schema、错误格式、事件、状态和端口 Schema。
- 集成测试：迁移、种子、会话、任务、checkpoint、Mock/沙箱回执和操作查询。
- 安全测试：未认证、跨租户/所有者、伪造上下文、提示注入、动态工具、重复请求和 fail-closed；基座阶段对确认/MFA/人工条件验证安全门拒绝或隔离夹具，不要求开放业务确认与写入闭环。
- 沙箱负向测试：网络、凭据、宿主文件/进程、资源超限和输出污染。
- 前端和 E2E 测试：登录、会话、任务状态、错误态、脱敏和占位交互。

CI 应运行格式/类型检查、架构依赖检查、契约检查、迁移/种子可复现、测试、秘密扫描、依赖与许可证扫描、前端构建和 Playwright 基础验证。关键安全门、事实一致性和审计测试失败时，禁止合并、发布或演示对应能力。

## 14. 推荐建设顺序

按依赖关系推进，避免先做页面或 Agent 再补安全底座：

1. **S0 工程基线**：仓库目录、锁文件、配置 Schema、Compose、脚本、README、CI 基础检查和追踪规则。
2. **S1 事实与契约**：Mock Core Banking、写沙箱协议/操作查询、OpenAPI/Schema、最小任务/审计持久化和确定性种子；写沙箱只验证隔离协议，不启用用户可调用的场景写能力。
3. **S2 安全执行骨架**：认证、租户/所有者、三道门、权限分级、确认/MFA/人工条件端口、幂等和 fail-closed；基座写能力仍保持关闭。
4. **S3 公共交互与编排**：React 页面壳、占位 API、LangGraph、checkpoint、任务恢复、状态时间线和回放。
5. **S4 场景接入**：按 R1 到 R6 逐域接入；每个场景独立路由、停用、测试和演示。
6. **S5 安全与质量验证**：红队、故障注入、并发/恢复/成本验证、对账、指标和告警。
7. **S6 演示与交付**：可重置 demo、演示脚本、README、架构图、核心算法说明、安全自评、测试材料、答辩 PPT 和视频。

## 15. 基座完成检查

满足以下条件后才进入六场景开发：

- 三套环境可以区分启动，目标数据库、端点和秘密命名空间隔离。
- 空库迁移、确定性种子、demo 重置和审计保留可重复验证。
- 前端能登录、建立/结束会话、发送占位消息、查看任务和统一状态。
- API 会话、租户、所有者和资源访问均由服务端重验；负向隔离测试通过。
- 输入门、工具门、输出门在真实请求链上，写能力默认关闭且不可旁路；基座只验证写路径在未满足条件时拒绝，不开放场景业务写处理器。
- Mock Core Banking 是唯一事实边界；基座不开放业务写操作，协议测试只使用本地隔离金融/礼品沙箱。
- checkpoint、任务、幂等、操作查询、审计和追踪标识能够关联和回放。
- liveness/readiness/能力状态可区分；审计或沙箱不可用时写请求被拒。
- 代码沙箱负向测试、秘密扫描、依赖扫描和架构依赖检查通过。
- README 可从干净环境启动、验证、停止和重置；文档明确列出当前占位范围。
- 没有真实金融路径、真实客户数据、生产凭据、伪造成功结果或把基座通过误报为业务完成。

基座退出后，由 DOC-CONTRACT-001、DOC-APP-001、DOC-DB-001、DOC-AGENT-001、DOC-TEST-001 和部署/安全自评文档分别承接字段、场景、状态机、测试和运维细节。任何新增写能力必须同时说明事实源/沙箱、风险等级、确认/MFA/人工条件、幂等策略、审计事件和验收证据。
