# 前端会话侧边栏 · 接口契约（v1）

> 对应后端 `Struct_of_Agent/web_test/server.py` 的 `/api/sessions*` 路由与
> `Struct_of_Agent/web_test/session_store.py` 的 `ChatSessionStore`。
> 后端 `API_VERSION = 2026-10-14.sessions-v3`，`features` 含 `sessions`。
> 页面 `Struct_of_Agent/web_test/index.html` 的左侧侧边栏按本文件实现。

## 1. 背景与目标

改造前，页面每次打开都用 `'web-' + Date.now()` 现造一个 `session_id`，服务端
也**没有任何会话列表**：

- 刷新页面 = 换一个新会话，上一轮对话再也回不去；
- R1/R2 的会话表虽然按 `session_id` 存了消息，却没有任何接口能把它读回来展示；
- R1 与 R2 的会话分处两个库文件，通用搜索（common）路径完全不落库，
  想拼一份「完整对话」需要同时查三处。

本契约定义一个**面向展示的会话层**，作为侧边栏唯一的数据来源：

- **会话注册表**：谁存在、叫什么、什么时候活跃、有多少条消息；
- **对话记录**：每条消息的角色、正文、命中的 Agent 与当时的模型信息。

它与 R1/R2 各自的 `ConversationStore` **并存、互不替代**：后者保存的是喂给模型的
多轮上下文（含 `tool_calls` / `tool_call_id`），前者保存的是给人看的记录。
两者靠同一个 `session_id` 关联 —— 侧边栏切回历史会话时复用原 `session_id`，
R1/R2 便会自然加载到该会话的上下文，多轮记忆由此保持。

## 2. 持久化

| 项 | 值 |
| --- | --- |
| 数据目录 | `Struct_of_Agent/web_test/data/`（环境变量 `BANK_AGENT_DATA_DIR` 可覆盖） |
| 会话库 | `<数据目录>/web_sessions.db`（SQLite） |
| R1 库 | `<数据目录>/r1.db`（会话 + 余额） |
| R2 库 | `<数据目录>/r2.db`（流水 + 报告 + 会话） |

**服务重启后历史仍在**（这是本功能的核心承诺，见 `tests/test_session_api.py`
的 `test_sessions_survive_a_real_process_restart`）。`web_test/data/` 已在
`.gitignore` 中忽略，不会入库。

演示账户余额改为「账户不存在时才播种」（`BalanceStore.ensure_account`），
重启不会把用户已经转出去的余额重置回 ¥1000.00。

接入 PostgreSQL 时，替换 `_build_supervisor()` 与 `get_session_store()` 里的
连接串即可，ORM 模型与仓储接口不变。

## 3. 统一响应包

`/api/sessions*` 的所有响应（含 4xx）都是统一响应包，与 `/api/settings/*` 一致：

```json
{ "ok": true, "message": "", "error_code": null, "data": { } }
```

失败时 `ok=false`、`error_code` 非空、`data=null`。**不使用** FastAPI 默认的
`{"detail": ...}` —— 否则前端只能显示「请求失败（HTTP 404）」，看不出是
「会话已被其它标签页删除」还是「标题为空」。

错误码：

| error_code | HTTP | 含义 |
| --- | --- | --- |
| `SESSION_NOT_FOUND` | 404 | 会话不存在或已被删除 |
| `SESSION_ID_INVALID` | 400 | `session_id` 不满足字符集/长度要求 |
| `SESSION_TITLE_INVALID` | 422 | 标题为空（或全是空白） |
| `SESSION_REQUEST_INVALID` | 422 | 请求体本身不合法（字段缺失/类型错误） |
| `SESSION_METHOD_NOT_ALLOWED` | 405 | 方法用错（如 `PUT /api/sessions`） |

> `POST /api/chat` 是**既有接口**，其响应形状与错误码不在本契约管辖范围内，
> 保持不变（请求体校验失败仍是 `LLM_CONFIG_INVALID`）。

## 4. 会话对象（session）

```json
{
  "id": "web-3f2a1c9d8e7b",
  "title": "给张三转账100元",
  "created_at": "2026-10-15T16:42:07",
  "updated_at": "2026-10-15T16:42:09",
  "message_count": 2,
  "preview": "已为您完成转账",
  "title_set_by_user": false
}
```

- `id`：`^[A-Za-z0-9_.:-]{1,64}$`。服务端生成形如 `web-<uuid4 前 12 位>`；
  但客户端自带 ID 也接受（向后兼容旧页面），不存在时自动补建。
- `title`：默认 `新会话`；首条用户消息折叠空白后截断到 24 字符（超出补 `…`）。
- `title_set_by_user`：为 `true` 时不再被自动标题覆盖（用户改过名 / 新建时指定了标题）。
- `message_count`：user + assistant 的条数。
- `preview`：最近一条消息的一行摘要（折叠空白，最多 60 字符）。
- 时间戳：本地时间 ISO 字符串（`timespec="seconds"`），字符串排序即时间排序。

## 5. 消息对象（message）

```json
{
  "role": "assistant",
  "content": "已为您完成转账",
  "created_at": "2026-10-15T16:42:09",
  "agent": "R1",
  "model_mode": "model",
  "model_name": "deepseek-chat",
  "tools": ["transfer_by_name"]
}
```

- `role`：`user` / `assistant`。
- `agent`：`R1` / `R2` / `common`，仅助手消息有。
- `model_mode` / `model_name`：生成该回复时的模型模式与模型名（来自 `trace`）。
- `tools`：该轮调用的工具名列表（来自 `trace.tool_names`），无工具时为空数组。

## 6. 接口清单

### 6.1 `GET /api/sessions` — 会话列表

按最近活跃倒序（`updated_at` 降序，同秒按自增主键降序）。

```json
{ "ok": true, "message": "", "error_code": null,
  "data": { "sessions": [ /* session 对象数组 */ ] } }
```

### 6.2 `POST /api/sessions` — 新建会话

请求体可省略，或 `{"title": "自定义标题"}`（`title` 可空）。

```json
{ "ok": true, "message": "已新建会话", "error_code": null,
  "data": { "session": { /* session 对象 */ } } }
```

**副作用**：创建前会删除所有 `message_count == 0` 的会话，避免用户连点
「新建会话」时侧边栏堆满「新会话」；已经说过话的会话不受影响。

### 6.3 `GET /api/sessions/{session_id}` — 会话详情

```json
{ "ok": true, "message": "", "error_code": null,
  "data": { "session": { }, "messages": [ /* message 对象数组，按写入顺序 */ ] } }
```

会话不存在 → 404 + `SESSION_NOT_FOUND`。

### 6.4 `PATCH /api/sessions/{session_id}` — 重命名

请求体 `{"title": "新标题"}`（必填，折叠空白后截断到 40 字符）。

```json
{ "ok": true, "message": "已重命名", "error_code": null,
  "data": { "session": { } } }
```

成功后 `title_set_by_user` 变为 `true`，后续消息不再改写标题。
空标题 → 422 + `SESSION_TITLE_INVALID`；会话不存在 → 404。

### 6.5 `DELETE /api/sessions/{session_id}` — 删除

```json
{ "ok": true, "message": "会话已删除", "error_code": null,
  "data": { "deleted": "web-3f2a1c9d8e7b" } }
```

删除会一并清掉该会话的对话记录，并调用 R1/R2 会话仓储的 `clear_session()`，
避免被删掉的会话仍在子 Agent 里留下「记忆」。上下文清理失败只打印告警，
不影响删除结果。会话不存在 → 404。

### 6.6 `POST /api/chat` — 既有接口，新增落库副作用

请求体与响应形状**完全不变**（`reply` / `blocked` / `moderation` / `tasks` /
`trace` / `agent`）。新增行为：

1. 会话不存在时按请求里的 `session_id` 自动补建（首条用户消息顺带生成标题）；
2. 把用户消息与助手回复写入会话库。

落库失败**绝不**影响本次对话：回复已经生成好了，侧边栏缺一条记录远好过整个
请求报 500，因此只打印一行告警。

### 6.7 版本握手

`GET /api/version` 与 `GET /health/live` 的 `features` 含 `sessions`。
页面遇到 `/api/sessions` 返回非统一响应包（旧进程 404）时，侧边栏显示
「历史会话读取失败」而不是一片空白。

## 7. 前端交互要求

| 交互 | 行为 |
| --- | --- |
| 页面加载 | `GET /api/sessions`；优先恢复 `localStorage['bank_agent.active_session']`，找不到则取最近活跃的一个；一个都没有则显示欢迎语（**不**凭空建会话） |
| 新建会话 | `POST /api/sessions` → 激活新会话、对话区回到欢迎语 |
| 点击历史条目 | `GET /api/sessions/{id}` → 渲染历史消息；重复点击当前会话不发请求 |
| 双击标题 / 铅笔按钮 | 就地变输入框；Enter 提交、Esc 取消、失焦提交；`PATCH` 后以服务端列表为准重绘 |
| 删除按钮 | 二次确认（`confirm`，文案含会话标题）；`DELETE` 成功后重绘；删掉的是当前会话则切到最近的一个，没有了就回到欢迎语 |
| 发送消息 | 没有当前会话时先 `POST /api/sessions`，再用该 `session_id` 调 `/api/chat`；结束后刷新列表以更新标题/条数/排序 |
| 收起 / 展开 | 侧边栏按钮切换 `.app.sidebar-collapsed`，状态记在 `localStorage['bank_agent.sidebar']`；未记忆过时窄屏（≤860px）默认收起，此时侧边栏是带遮罩的抽屉 |
| 接口不可用 | 显示「历史会话读取失败」+ 后端原因，对话框本身仍可用，不弹 `alert` |

## 8. 安全与工程约束（硬性）

1. **会话 ID 白名单**：`^[A-Za-z0-9_.:-]{1,64}$`，在路由层先校验再进仓储，
   杜绝路径穿越与不可见字符。
2. **不落密钥**：会话库只存对话正文与模型名/模式，绝不存 API Key；
   `_record_turn` / `_clear_agent_context` 的告警日志也不含密钥。
3. **统一响应包**：见第 3 节，所有 4xx 都必须带 `ok` / `error_code`。
4. **前端零外部依赖**：侧边栏只用原生 DOM API，不引入任何前端框架或 CDN。
5. **用户内容一律走 `textContent`**：只有内置的 SVG 图标字符串允许进 `innerHTML`。

## 9. 并发与一致性

FastAPI 的同步路由跑在线程池里，同一个会话可能被多个请求同时碰到，
仓储因此必须自己扛住并发（已用 24 线程 × 6 请求压测验证）：

1. **写消息对「清理空会话」免疫**。`append_message` 是「先 SELECT 再 UPDATE」，
   而 pysqlite 默认只在 DML 时才真正开启事务 —— 那次 SELECT 不持锁，
   另一个请求的 `create_session`（它会清理 0 条消息的空会话）可以正好落在
   两步之间，让 UPDATE 命中 0 行并抛 `StaleDataError`。
   **仓储遇到这种冲突会自动重试一次**（重试时把会话重新建出来）。
   没有这道重试，接口照样返回 200，消息却静默丢失 —— 这是压测抓出来的真实故障。
2. **删除是幂等的**。`_purge` 用 Core `DELETE` 而不是逐行 `session.delete(row)`：
   并发重复删除时逐行删除会因「期望删 N 行、实际 0 行」刷 SAWarning。
3. **删除/读取一个刚被清理掉的会话返回 404 `SESSION_NOT_FOUND`，这是正常结果**，
   不是故障。前端对此有明确处理：切换时回到欢迎态并刷新列表，删除时给侧边栏提示。
   触发条件是「同一瞬间既在新建会话、又在对另一个空会话发首条消息」，
   单用户正常使用碰不到。
4. **写入失败绝不影响对话**：`_record_turn` 吞掉异常只打印一行告警，
   宁可侧边栏少一条记录，也不让已经生成好的回复变成 500。
