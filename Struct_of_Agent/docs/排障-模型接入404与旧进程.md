# 排障：模型接入「保存后不生效 / 测试连接报 HTTP 404」

> 适用现象：在页面「模型设置」里填好 Base URL、API Key、模型名后，
> **测试连接**与**保存并启用**都失败，弹窗内出现红框
> `请求失败（HTTP 404）`，且「联网搜索接入（可选）」的徽标一直停在 `读取中…`。

## 1. 结论（先说答案）

**这不是配置问题，也不是模型/网关问题，而是「浏览器里的新页面」连到了「旧代码的服务进程」。**

页面 `web_test/index.html` 是由后端用 `FileResponse` **每次请求时从磁盘读取**的，
而 `/api/settings/*` 这些路由是**进程启动时**注册的。于是会出现一种很隐蔽的错配：

| | 来源 | 版本 |
| --- | --- | --- |
| 页面（HTML/JS） | 每次请求从磁盘读 | **最新**（有模型设置面板） |
| 接口（路由表） | 进程启动时固定 | **旧版**（没有 `/api/settings/*`） |

结果：面板画得出来，但一调接口就是 404。FastAPI 对未知路径返回的是
`{"detail":"Not Found"}`，页面拿不到契约里的 `ok`/`message` 字段，
只能兜底显示一句没有信息量的 `请求失败（HTTP 404）`；
搜索徽标则因为 `GET /api/settings/search` 同样 404、从未被赋值，永远停在 `读取中…`。

## 2. 三步确认（30 秒）

```powershell
# ① 接口是否注册（旧进程会返回 {"detail":"Not Found"}）
curl.exe -s http://127.0.0.1:8000/api/settings/llm

# ② 健康检查是否带 model_mode / api_version（旧进程只有 {"status":"ok"}）
curl.exe -s http://127.0.0.1:8000/health/live

# ③ 谁在占着 8000 端口、是什么时候启动的
Get-NetTCPConnection -LocalPort 8000 -State Listen |
  Select-Object OwningProcess
Get-CimInstance Win32_Process -Filter "Name like '%python%'" |
  Select-Object ProcessId, CreationDate, CommandLine
```

判据：

- ① 返回 `{"detail":"Not Found"}` → **后端是旧进程**（本文档描述的场景）；
- ① 返回 `{"ok":true,...}` 且 ② 带 `model_mode` / `api_version` → 后端正常，
  请改看错误码（见第 5 节）；
- ③ 中 `CreationDate` 早于你最后一次修改 `web_test/server.py` 的时间 → 旧进程无疑。

## 3. 修复：重启服务

```powershell
# 方式一：一键脚本（推荐，自动只结束 web_test\server.py 进程并等待新版本就绪）
cd D:\Bank-Agent\Struct_of_Agent
powershell -ExecutionPolicy Bypass -File web_test\restart_server.ps1

# 方式二：手动
#   1) 关掉旧进程所在的终端窗口（或结束进程）
#   2) 重新启动
python web_test/server.py
```

重启后浏览器 **F5 刷新**，再点右上角齿轮：徽标应显示 `未配置模型`（而不是报错），
`GET /api/settings/llm` 应返回 `{"ok":true,...}`。

> 注意：`python web_test/server.py` 要在 `Struct_of_Agent` 目录下执行；
> 在仓库根目录 `D:\Bank-Agent` 下执行会因为找不到 `web_test` 而直接失败。

## 4. 为什么密钥不用重填两次

运行时的 Base URL / API Key / 模型名只保存在**服务进程内存**里（设计约束：不落盘、
不写日志、不写浏览器存储）。因此：

- **重启服务 = 运行时配置清空**，需要重新点一次「保存并启用」；
- 页面会记住**非密钥**偏好（`localStorage` 键 `bank_agent.llm.pref`，只存
  `base_url` / `model` / `response_format`），所以重启后 Base URL 与模型名会自动回填，
  只需重新粘贴 API Key。

## 5. 如果重启后仍然失败，看错误码

接口返回的是契约里的统一响应包，`error_code` 直接指明原因：

| error_code | 含义 | 处理 |
| --- | --- | --- |
| `LLM_KEY_REQUIRED` | 没填 Key，且环境变量里也没有 | 粘贴 API Key |
| `LLM_AUTH_FAILED` | Key 无效 / 无该模型权限（401、403） | 换 Key，或确认该 Key 是否开通了此模型 |
| `LLM_MODEL_NOT_FOUND` | Base URL 路径或模型名不对（404） | 用 `GET <base_url>/models` 核对模型名 |
| `LLM_CONNECTION_FAILED` | 域名/端口不可达、DNS 或代理问题 | 检查网络、Base URL 拼写 |
| `LLM_TIMEOUT` | 上游首字节慢（实测常态 1.3~5.8 秒，多轮大 prompt 偶发 32~36 秒） | 调大「超时（秒）」（默认已 120）；**与 Base URL / API Key / 模型名无关** |
| `LLM_RATE_LIMITED` | 限流/额度不足（429） | 稍后重试或换 Key |
| `LLM_CONFIG_INVALID` | 字段格式非法（URL、模型名、数值越界） | 按提示修正 |
| `BACKEND_OUTDATED` | 该接口在当前进程里不存在 | **就是本文档的场景：重启服务** |

常用自检命令（把 Base URL 换成你自己的）：

```powershell
# 该网关支持哪些模型？（能确认模型名拼写）
curl.exe -s -H "Authorization: Bearer <你的Key>" https://api.a6api.com/v1/models
```

## 6. 本次排障的实际证据（2026-10-15）

| 检查 | 旧进程（:8000） | 新代码（:8010 临时实例） |
| --- | --- | --- |
| `GET /health/live` | `{"status":"ok"}`（无 `model_mode`） | `{"status":"ok","model_mode":"mock",...}` |
| `GET /api/settings/llm` | `{"detail":"Not Found"}` → **404** | `{"ok":true,...}` → **200** |
| 进程启动时间 | 2026-10-13 22:01（早于设置功能落地） | — |

用同一套 `https://api.a6api.com/v1` + `deepseek-v4.1-flash` 在**新代码**上实测：

- `GET /v1/models` → 200，共 128 个模型，**包含** `deepseek-v4.1-flash`；
- `PUT /api/settings/llm` → `ok:true`，`mode:model`；
- `POST /api/settings/llm/test` → `ok:true`，`latency_ms≈3400`，`reply:"pong"`；
- `POST /api/chat`（真实模型）→ `trace.model_mode=model`、`model_name=deepseek-v4.1-flash`；
- R1 转账 / R2 账单两条路径同样 `model_mode=model`，功能正常；
- 全流程所有响应体中**未出现明文 API Key**（接口只回掩码 `sk-...G9E7`）。

即：**代码本身没有问题，问题只在「跑的是旧进程」。**

## 7. 本次修复：让这种错配再也不会「静默」

代码侧没有业务缺陷，但「页面新版 + 后端旧进程」之所以难查，是因为失败信息被吞掉了。
本次补齐了三层自诊断与一层韧性：

| 能力 | 位置 | 作用 |
| --- | --- | --- |
| **页面加载即检测旧后端** | `index.html` 的 `#staleBackendBanner` | 打开页面就调 `/health/live`：返回里**没有 `api_version`** → 顶部红色警示条，直接给出重启命令与脚本路径（旧进程只会返回 `{"status":"ok"}`，所以这个信号零误报） |
| **面板 404 说清原因** | `index.html` 的 `callApi()` | 不再是干巴巴的 `请求失败（HTTP 404）`，而是 `后端返回错误（HTTP 404）：Not Found；当前后端服务是旧版本，未注册该接口，请重启服务：python web_test/server.py` |
| **未注册路径自解释** | `server.py` 的 `StarletteHTTPException` 处理器 | `/api/settings/*` 未注册 → `{"ok":false,"error_code":"BACKEND_OUTDATED",...}`；其它路径的 404/405 行为不变 |
| **版本握手** | `server.py`：`API_VERSION` / `API_FEATURES` | `GET /health/live` 追加 `api_version` + `features`；新增 `GET /api/version`；启动时打印一行版本与已注册设置路由（不含任何密钥） |
| **一键重启** | `web_test/restart_server.ps1` / `.bat` | 只结束命令行匹配 `web_test[\/]server.py` 的本项目进程（绝不误杀无关 python），确认端口空闲后脱离 shell 启动，并轮询 `/health/live` 直到 `api_version` 与源码一致 |
| **不再卡「读取中…」** | `index.html` | 所有 `/api/settings/*` 请求带 `AbortController` + 计时器兜底（即使 `fetch` 永不 settle 也一定返回）；读取失败时徽标落到 `读取失败`，后端整体不可达时顶栏显示 `后端不可用` |
| **前端探测超时自适应** | `index.html` 的 `probeTimeoutMs()` | 后端会按页面填的「超时（秒）」等上游（契约上限 300 秒）。前端固定 60 秒会在慢网关上**假超时**（实测该网关探测耗时 3.4 ~ 21.6 秒），故前端取 `max(60 秒, 表单超时 + 10 秒)` |

回归护栏（全部实测通过）：

```powershell
# 后端：155 个用例（含新增的版本握手 / 404 语义 / 真实 socket 端到端热切换）
& .venv\Scripts\python.exe -m pytest tests -q

# 前端：182 项 DOM 检查（jsdom，含旧后端警示条、404 文案、超时兜底、探测超时自适应）
node tests\frontend\test_settings_panel.mjs
```

其中 `tests/test_server_http_e2e.py` 用真实 uvicorn + 真实 socket 跑完
「保存 → 测试连接 → 对话使用新模型」，并做过**证伪**：把应用换成「只有
`/health/live` 与 `/api/chat` 的旧进程」时该用例集 6 失败 1 通过，报错正是
`AssertionError: {"detail":"Not Found"}`——即用户遇到的那个症状。

## 8. 另一个故障：对话显示「请求失败：network error」（2026-10-19）

**现象**：配好 API Key 后发消息，气泡里显示 `请求失败：network error`；浏览器网络面板里
`POST /api/chat/stream` 是 **HTTP 200**，但响应体为空、连接随即中断。

**根因**：`web_test/server.py` 的流式接口直接引用了模块级 `_supervisor`，而它由
`get_supervisor()` **惰性创建**。页面发消息只走流式接口，所以 `_supervisor` 一直是
`None`，生成器第一次迭代就抛 `AttributeError`。此时 200 响应头已经发出，Starlette
只能掐断连接，前端 `fetch` 读流时抛 `TypeError: network error`——与 API Key、
Base URL、模型名都无关。

**修复**：

| 位置 | 改动 |
| --- | --- |
| `web_test/server.py` | 流式接口改为 `get_supervisor()`，首个请求即创建调度器 |
| `web_test/server.py` | 生成器异常改为推 SSE `error` 事件并以 `[DONE]` 收尾，不再断流 |
| `web_test/server.py` | 调度器初始化失败返回 503 统一响应包（`CHAT_UNAVAILABLE`），而不是空流 |
| `db/session.py` / `alembic.ini` | Alembic `script_location` 固定为仓库内绝对路径：重启脚本以 `Struct_of_Agent` 为工作目录时，旧写法会抛 `Path doesn't exist: .../Struct_of_Agent/migrations`，首个对话请求同样 503 |

**验证**（重启后执行，返回一串 `data: {...}` 并以 `data: [DONE]` 结束即正常）：

```powershell
curl.exe -s -N -X POST http://127.0.0.1:8000/api/chat/stream `
  -H "Content-Type: application/json" `
  -d '{\"message\":\"你好鸭\",\"session_id\":\"smoke\"}'
```

回归护栏：`tests/test_server_stream.py`（首个流式请求、流内异常、初始化失败）、
`tests/test_server_http_e2e.py::test_chat_stream_works_on_the_first_request_with_a_saved_model`
（真实 socket + 假 OpenAI 上游 + 流式 SSE）、
`tests/test_db_units.py::test_head_revision_works_from_any_working_directory`。

> 提醒：重启服务会清空**内存中**的运行时模型配置，需要在「模型设置」里重新粘贴一次
> API Key（Base URL 与模型名会从 localStorage 自动回填）。

## 9. 另一个故障：对话回复「模型调用失败…Request timed out.」（2026-11-01）

**现象**：发消息后气泡（以及执行计划节点）显示

```
模型调用失败，未能完成本次请求：Request timed out.
请检查「模型设置」中的 Base URL、API Key 与模型名是否正确。
```

重发同一条消息有时又能成功；「测试连接」始终正常。

**为什么提示误导**：这句建议是**兜底文案**，无论何种失败都套用。它把「上游慢」写成了
「配置写错」，把排查引向 Base URL / API Key / 模型名——而这三项其实都是对的。

**根因（旁路代理逐请求计时，非推断）**：在 `127.0.0.1:8899` 起一个转发代理，把运行时
`base_url` 临时指过去，记录每次上游请求的时间到首字节（TTFB）：

| 请求体大小 | TTFB |
| --- | --- |
| 126 B ~ 2.4 KB（规划、闲聊、短问答） | 1.3 ~ 5.8 秒 |
| 8 ~ 15 KB（带工具结果的多轮 Agent 调用） | 多数 4~6 秒，但**偶发 32.0 / 35.0 / 35.9 秒** |

于是：

1. 应用侧超时当时是 **30 秒**，上游 32~36 秒的抖动**必然**被掐断；
2. `openai` SDK 默认 `max_retries=2`，一次超时被放大成 **3 次 × 30 秒**的静默等待
   （代理日志里能看到同一 `body` 连打三遍、前两次都是 `ttfb≈32~35s` 后被客户端 abort）；
3. 三次都没赶上快路径 → 约 90~110 秒后抛 `Request timed out.` → 节点被标死「失败」。
   实测最差一次：`[你好] total=96.4s → FAILED: Request timed out.`

**修复**：

| 位置 | 改动 | 为什么 |
| --- | --- | --- |
| `common/runtime_config.py` / `common/config.py` | 默认超时 `30.0` → **`120.0`**（范围仍 1~300） | 120 秒 > 实测 36 秒尾延迟的 3 倍余量；环境变量与运行时两条配置路径同值 |
| `common/llm.py` | 显式 `max_retries=0`；超时改传 `httpx.Timeout(read=配置值, connect=min(15, 配置值), ...)` | 重试预算只由「超时（秒）」决定，最坏墙钟从 ~3× 变回 1×，也避免同一请求重复计费 |
| `common/model_manager.py` | `classify_model_error` 增加文本判类（`timed out` / `timeout` / `超时` → `LLM_TIMEOUT`，连接类 → `LLM_CONNECTION_FAILED`） | 流式链路只透传 `str(exc)`，异常类型已丢失，否则超时会被归到 `LLM_REQUEST_FAILED` |
| `supervisor.py` | 失败提示按错误码分流（`_failure_hint`）；超时明确写「不是 Base URL / API Key / 模型名的问题」，并给出调大「超时（秒）」与「写操作先核对再重试」的指引；`trace.error_code` 记录错误码 | 让用户在第一屏就拿到正确方向 |
| `web_test/index.html` + 三篇文档 | 占位符/默认值/文案同步 30 → 120；探测超时自适应也随之变为 `max(60 秒, 120+10 秒)` | 前后端口径一致 |

**回归护栏**：`tests/unit/test_model_timeout_diagnosis.py`（默认值、异常类型丢失时的归类、
`max_retries==0`、`read/connect` 预算、超时提示不得再提 Base URL / API Key / 模型名、
未知错误仍保留原兜底文案）；契约测试里 4 处 `30.0` 快照断言同步为 `120.0`。

**还剩一个已知限制**：`common/plan.py` 的 `PlanNode.timeout_s` 目前只参与序列化，
执行期没有墙钟实现——节点级超时若要生效，需另行补齐。
